# 需求原文图片识别（图 → 文字）设计方案

> 状态：**设计定稿，未落地**（2026-10-21，二稿：砍掉 vision_model 子槽与 AI 设置页改动，视觉调用直接用现有主模型）。落地前/落地时凡碰需求单表单、feed 附件、llm_client 能力档案任一处，先读本文。
>
> 结论口径：**视觉调用直接用 `llm_config` 现有主模型**（用户拍板：现配模型已支持图片识别），不改模型连接配置；只补「图片→文字」一环；识别结果永远以**可编辑草稿**进需求原文，经人工确认、随需求单**显式提交**才落库；结构化抽取继续走既有文字管线，不在视觉调用里造第二套抽取。

## 一、背景与动机

业务现状：客户需求基本通过邮件到达，业务员往平台录入时是"贴一张带字的图"（邮件截图/微信截图/报价单截图），频率很高。

两个层面的问题：

1. **录入侧**：图里的字靠手敲进需求原文，一张配置截图 5~10 分钟，数字易抄错（256G→265G 这类错误会顺着管线流进报价，比慢更危险）。
2. **分析侧（战略）**：平台后续的 AI 能力（需求理解/选型/方案对照）都以**需求原文文字 + 商机方案**为原料——`llm_extract_enhance.py` 的文字抽取管线、规则词表、知识注入全部只吃文字。图停留在附件里 = 这单的需求对 AI 不可见。

现状链路（2026-10-21 已核实）：

- 需求原文是自由文本"客户原话"（`frontend/src/components/flow/RequirementForm.vue:347`，hint 明确"后端仅辅助交叉校验"），表单提供 `after-req-text` 插槽（:356）。
- 图片已可进需求单：需求附件条 `frontend/src/components/opportunity/RequirementAttachmentChips.vue` 支持上传/拖拽/**Ctrl+V 粘贴截图**（:120），png/jpg 在 ACCEPT 白名单（:30），附件钉需求单版本随版留档。**但图只是留档，文字不会进原文**。
- 宿主：`frontend/src/components/opportunity/OpportunityProcessBoard.vue` 需求单 modal，两个 RequirementForm 实例同源 `v-model:req-text="reqText"`（:1315/:1339），Chips 嵌在 `#after-req-text` 插槽。
- 文字→结构化管线现成：`backend/app/services/llm_extract_enhance.py`（schema 收口 + 规则兜底）。
- LLM 接入框架现成：`backend/app/services/llm_client.py` 双协议（`upstream_format` openai/anthropic 分流，:168），全链路目前纯文本；能力档案（:182 BUILTIN_MODEL_CAPABILITIES + `probe_capabilities` 实测注入）尚无视觉档位——本方案为其补 `supports_vision` 一档（§五）。

→ 缺的只有「图片→文字」一环。补上它，整条链贯通：**贴图 → 识别成原文草稿 → 人工确认 →（既有）AI 结构化抽取 → 报价**。

## 二、方案总览

```
邮件截图 ──粘贴/上传──▶ 需求附件（已有，钉版本留档）
                            │ 点「提取文字」
                            ▼
              POST /api/feed/attachments/{id}/ocr
                            │ 视觉调用：llm_config 主模型（openai/anthropic 双协议照旧分流）
                            │ 识别文本
                            ▼
              「识别结果」确认弹层（可编辑，追加/替换）
                            │ 人工确认
                            ▼
              需求原文草稿 ──显式提交──▶ requirements
                            │（既有管线，本期不动）
                            ▼
              规则抽取 + llm_extract_enhance → 结构化 slots → 选型/报价/AI 分析
```

设计原则（三条，落地时不许破）：

1. **只做一环**：本期只做"图→文字"。识别结果进需求原文后，结构化仍走既有文字管线；不在视觉调用里新增抽取逻辑。
2. **人工确认闸门**：识别文本必须经过"结果确认弹层（可编辑）→ 填入草稿"，填入后仍是表单草稿态，最终随需求单**显式提交**。任何路径不允许识别结果直落库。
3. **复用最大，配置零新增**：不新增视觉模型配置、不动 AI 设置页的模型连接区；视觉调用与主模型共用同一份 `llm_config`（model/base_url/api_key/upstream_format 全部照旧）；鉴权/存储/附件语义复用 feed 现有端点族；双协议调用复用 `llm_client` / `anthropic_channel` 基元。

**技术选型定论：多模态大模型，不自建传统 OCR。** Tesseract/PaddleOCR 需新增重依赖 + 模型维护，对中文截图（聊天气泡、表格线、低分辨率）效果明显弱于视觉模型；且视觉模型可按提示词过滤界面噪音（时间戳/昵称/按钮），传统 OCR 做不到。

## 三、交互设计（前端）

范围：商机详情页需求单 modal（`OpportunityProcessBoard` 内的 `RequirementAttachmentChips`）。业务门户（portal）侧需求表单暂不铺。

入口：

- 图片徽标 hover 出现「提取文字」action（与现有 ✕ 同级，样式走 chip 既有 token）；
- 附件预览弹层内放主按钮「提取文字到需求原文」（预览时用户正看着图，是自然时机）；
- `readonly`（已归档查看）态不出现入口。

状态机：点击 → 按钮 loading（防重复点击）→ 成功弹「识别结果」确认层 / 失败 toast 归一文案（§四）并复位可重试。

确认弹层（新组件，线框）：

```
┌ 识别结果 · 截图.png ──────────────────────────┐
│ 请核对数字与型号；识别结果将作为草稿填入需求原文 │
│ ┌ textarea（预填识别文本，可编辑，minRows 6）─┐ │
│ └────────────────────────────────────────────┘ │
│ 插入方式： (•) 追加到原文   ( ) 替换原文         │
│                            [取消] [填入需求原文] │
└────────────────────────────────────────────────┘
```

插入规则：

- 原文为空 → 直接填充（按钮文案统一"填入需求原文"）；
- 追加 → 原文末尾补一个空行后拼接（**不加任何分隔标记**，原文保持"客户原话"纯净文本；来源由附件区自然承载）；
- 替换 → 整体覆盖（选替换时弹层内给出覆盖提醒文案）；
- 写入目标是 `OpportunityProcessBoard` 的 `reqText`（两实例同源 v-model，见 §一锚点）。

多图：本期只做单图逐张提取（多张 = 多次点击追加）；批量提取不做（未来有需要另立方案）。

大图：发起前按 `file_size` 预检，> 6MB 直接提示"图片过大，建议用截图工具重新截图后粘贴"（主流视觉端点 base64 图上限约 5MB；截图通常 < 2MB）。服务端压缩需引 Pillow，本期不做。

错误文案（归一，可操作）：

- 模型不支持图片（能力档案 `supports_vision=false`，或调用被上游拒绝）：「当前接入的模型不支持图片识别，请在 AI办公室 → 模型与接入 更换支持多模态的模型后重试」；
- 超时/网络：「识别超时，请重试」；
- 模型未返回文本：「识别结果为空，请重试或手动录入」。

## 四、后端设计

### 端点

`POST /api/feed/attachments/{attachment_id}/ocr`（挂在 `backend/app/api/feed.py` 附件端点族）：

- **鉴权**：`ensure_opportunity_access(att.opportunity_id)` + `_ensure_category_visible`——与 `download_attachment`（feed.py:316）完全同款；
- **校验**：`mime_type` 白名单 image/png|jpeg|webp|gif|bmp；`file_size` > 6MB → 400（带 §三文案）；
- **取字节**：`get_storage().resolve_local_path(storage_key)` 读盘；仅对象存储部署走 `presigned_url` 拉取（与下载端点同判据，feed.py:327-333）；
- 调 `vision_ocr.ocr_image(data, media_type)`；
- **返回**：`{"text": "...", "model": "<实际用的模型名>"}`；
- **审计日志**：logging 记 user_id / attachment_id / model / 返回文本长度（不记全文——正文随后会进需求原文，有留档处）；
- **不落库**（无迁移）：识别文本经确认后进需求原文、随需求单持久化，附件表不加列；重复识别成本分钱级可接受。

### vision_ocr.py（新文件）

新文件理由：视觉识别是独立能力面（图片装载、提示词、双协议视觉消息、结果清洗），收口一处；`llm_client.py` 保持"纯文本契约"不动（只按 §五加能力档位），避免动全平台热路径。

配置读取：**直接 `_get_llm_config()` 用主模型全套**（model/base_url/api_key/upstream_format/thinking 语义照旧）——不加任何子槽、不做回落判断。

能力预检：`get_model_capabilities()` 取 `supports_vision`，为 `False`（有实测证据不支持）时直接抛 `VisionOCRError("当前模型不支持图片识别…")`，不发无效请求。**默认乐观**：无实测证据时档案值为 True、不拦截（误拦的代价是功能不可用，误放的代价只是一次可重试的报错——见 §五探测语义）。

消息构造（内部统一 OpenAI content-parts 形态，再按协议分流）：

- **openai 路径**：复用 `llm_client._client(base_url, api_key)`（trust_env=False 直连等既有语义），非流式 `chat.completions.create`，`content=[{type:"text",text:prompt},{type:"image_url",image_url:{url:"data:{mime};base64,..."}}]`；
- **anthropic 路径**：复用 `anthropic_channel` 的 `messages_base`/headers/`_raise_for_status`/`_wrapped_error`/`_parse_nonstream` 基元，图片走 image block：`{"type":"image","source":{"type":"base64","media_type":mime,"data":...}}`。**视觉调用自建 payload，不经过 `to_anthropic_messages`**（该函数面向纯文本消息，不为视觉扩形，不碰全平台热路径）。

prompt（常量，temperature=0）：

```
你是 OCR 转写助手。逐行提取图片中的全部文字：
1. 忠实转写：不翻译、不总结、不改写、不补全、不加任何评论；
2. 数字、型号、单位逐字符精确（例：256G、4TB NVMe、EPYC 9254、双电源）；
3. 聊天/邮件截图：忽略昵称、时间戳、表情、按钮等界面元素，只保留需求正文；
4. 表格按行转写，单元格之间用「 | 」分隔；
5. 无法辨认的字符用 □ 占位，不要猜；
6. 只输出转写文本，不要代码块标记、不要说明。
```

参数：temperature 0，max_tokens 4096，timeout 90s，max_retries 0（与 `_client` 一致），单图单发非流式。

输出清洗：剥 markdown code fence（部分视觉模型爱包 ```）、strip 首尾空白；空结果 → `VisionOCRError("模型未返回文本")`。

错误归一：上游异常（401/404、400 含 image/not support、连接/超时）统一归一为 `VisionOCRError(用户可读文案)`，HTTP 层映射 4xx/502；**禁止把上游堆栈透给前端**。上游对图片报"不支持"类错误时，顺带把该 model@端点 的 `supports_vision` 实测结果置 False（与 §五探测同源，避免下次再撞）。

### 涉及面（后端）

- 新文件 `backend/app/services/vision_ocr.py`（理由如上）；
- `backend/app/api/feed.py` +1 端点（理由：附件子资源，鉴权/存储复用度最高，不另开路由文件）；
- `backend/app/services/llm_client.py`：能力档案加 `supports_vision` 键（内置表 + 默认值 + `get_model_capabilities` 合并逻辑，改动量小且纯增量）；
- 无 DB 迁移、无新依赖（Pillow 不引）、**AI 设置页模型连接配置零改动**。

## 五、模型能力档案：新增「多模态」探测档

范围仅此一处设置面（用户拍板：模型配置不动，能力档案补探测）：

- `BUILTIN_MODEL_CAPABILITIES` / `DEFAULT_MODEL_CAPABILITIES`（llm_client.py:182-226）增加 `supports_vision` 键；**内置家族值一律 True（乐观默认）**——家族名判不出具体模型是否视觉版，误拦比误放代价高；
- 探测：现有 `/api/system-config/llm_config/probe` 机制（system_config.py:391，实测结果经 `probe_capabilities` 注入 `get_model_capabilities`）扩展一项——发一张 1×1 px PNG base64 小图：
  - 上游 2xx 且有文本返回 → `supports_vision=true`（实测）；
  - 400/404/422 且错误含 image/unsupported 类语义 → `supports_vision=false`（实测）；
  - 网络/鉴权等其他失败 → **不改档**（保持乐观默认，探测历史照常记录失败原因）；
- `AiSettingsPanel.vue`（同一面板组件有两个宿主：AI办公室 →「模型与接入」内嵌，及独立 `/ai-settings` 页）的「模型能力档案」tab（AiSettingsPanel.vue:120）新增一行「多模态」展示——**只加展示档位，不加任何配置输入**；
- 消费方：`vision_ocr` 预检（§四）+ 需求单侧识别失败文案归一（§三）。

## 六、安全与合规

- 图片与需求原文走**完全相同**的 LLM 通道（同模型、同账号、同 base_url），合规面零扩大；
- 附件读取走既有商机访问权 + 分类可见性双重校验；
- 识别结果不落库、不进日志正文；
- 前端不向识别端点以外的任何地方发送原图。

## 七、成本

一张典型需求截图 ≈ 1000~3000 视觉 token，单次 ≈ 几厘到几分钱；触发频率 = 业务员主动点击，无放大效应。可忽略，不做配额。

## 八、分期

- **P0（本期，本文全部范围）**：图片文字解析——OCR 端点 + `vision_ocr.py` + 前端提取入口/确认弹层/插入规则 + 能力档案 `supports_vision` 探测档。
- **明确不做（未来需要时另立方案）**：识别时顺带产出结构化配置草稿（走视觉模型直出 JSON 预填配置区）；批量多图提取；识别结果缓存落库；xlsx/pdf 附件文字解析；业务门户侧入口；存量纯图附件批量回填；自动提交；服务端图片压缩。
- AI办公室「模型与接入」的模型连接配置：**不改**（已由用户拍板）。

## 九、测试与验收

单测（fake repo / mock LLM，不真调上游）：mime 白名单、size 拒绝、`supports_vision=false` 预检文案、openai/anthropic 两路径 payload 构造与输出清洗、错误归一（401/不支持图/超时/空文本）、能力档案合并（内置乐观默认 + 实测覆盖）、探测三种结局（2xx / 明确拒绝 / 网络失败不改档）、鉴权 403/404。

手动验收清单：

1. 微信截图粘贴 → 提取 → 数字/型号逐字符一致；
2. 原文非空追加（空行分隔）与替换两路径均正确；识别后不提交、直接关弹窗，原文无残留脏改；
3. 已归档 readonly 无入口；无商机权限者 403；
4. 能力档案探测：现配模型探测为「多模态 ✓」；识别全链走通；
5. `upstream_format` openai 与 anthropic 两种上游各过一遍（当前配置为哪种就验哪种，另一种以单测覆盖 payload 构造）；
6. 识别 → 填入 → 提交需求单全链回归：附件与需求单版本钉住、既有抽取管线不受影响。

## 十、风险与对策

| 风险 | 对策 |
| --- | --- |
| 识别错数字流进报价 | 确认弹层人工核对 + 草稿态 + 显式提交三道闸；prompt 强调数字逐字符精确、认不准用 □ |
| 主模型实际不支持多模态（与用户认知不符） | 能力档案 `supports_vision` 提前提示 + 调用报错归一为可操作文案（指引换模型）；识别无副作用，换好模型即恢复 |
| 上游对图限流/偶发失败 | 错误归一 + 重试幂等（识别无副作用） |
| 大图超上游上限 | 6MB 前置预检 + 引导重截；服务端压缩不做（届时引 Pillow 并单独给理由） |
| 探测误判（网络抖动记成不支持） | 探测仅在上游**明确拒绝图片**时才置 False；网络/鉴权失败不改档；可重跑探测修正 |
