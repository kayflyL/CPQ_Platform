## 0. 三句话总纲

1. **现状**：AI 办公室（工作流引擎）和 CPQ 业务是**长在一起**的，所以每加一条工作流都费劲，AI 搭流还会漏东西（这次的空抽屉就是这么来的）。
2. **目标**：把"系统该干的"和"业务该干的"拆开。AI 办公室变成一个**强壮的引擎**（像安卓系统），CPQ 变成它上面的**第一个 App**，以后人事培训系统就是第二个 App。
3. **怎么去**：六步走（§6），每步做完系统都照常能用、可回滚——不推倒重写。

## 1. 一个你亲历过的比喻：安卓系统与 App

你写过鹦鹉日记这个安卓 App，所以这个比喻你全套都懂：

| 安卓世界 | 我们的世界 |
|---|---|
| 安卓系统（管 App 生死、权限弹窗、应用商店审核） | **AI 办公室引擎**（管工作流推进、确认卡、审计、画布） |
| 鹦鹉日记 App | **CPQ**（第一个 App） |
| 以后写的某个新 App | **人事培训系统**（第二个 App） |
| AndroidManifest.xml（App 声明"我要用相机、我要存本地"） | **接入声明**（系统声明"我让 AI 干哪些活、哪些页面给它看、权限到哪"） |
| 运行时权限弹窗（App 要开相机 → 系统弹窗问你 → 你批了才开） | **确认卡**（AI 要改价 → 系统弹卡问你 → 你批了才改） |
| 应用商店审核（声明不全不让上架） | **发布校验器**（工作流声明不全不让上线） |
| ContentProvider（App 对外提供数据的标准接口） | **工具**（业务系统提供给 AI 的标准操作，如"查配件价"） |

关键事实：**你从来没改过安卓系统一行代码，但你的 App 能用相机**——因为系统提前做好了相机接口和权限弹窗，你只需要声明。我们要达到的就是这个效果：CPQ 和将来的任何系统，都只做"声明"，不改引擎。

CPQ 今天的问题打个比方：现在的引擎和业务像**相机驱动焊死在 App 里**——能用，但每换一个 App 都要重焊一遍（每加一条工作流都费劲），而且焊得对不对只有试了才知道（AI 漏东西、用户实测发现）。改造就是**拆焊，不是重造**：现有页面、现有数据库、现有规则全都不动，只是给它们"办入网登记"。

## 2. 直接回答你的问题："是有类似 API 的东西提前写好吗？"

**对。但先把分工说死：调用 AI、弹确认卡、记审计这些机制全是引擎（AI 办公室）的活，业务系统一辈子不写这类代码；业务系统只出两样东西——功能本体（服务层的业务函数）和一份声明表。"AI 工具"诞生在两者的交点上，不是业务系统加出来的功能。** 引擎要提前写好三样东西，一次写好，所有系统受益：

| # | 东西 | 类比 | 它管什么 |
|---|---|---|---|
| 1 | **接入声明格式** | AndroidManifest.xml | 一个系统想接入 AI，照格式填三张清单：①工具清单（我能让 AI 干什么活，每个标注"读还是写、要不要确认"）②页面清单（我的哪些界面能给 AI 当"产物窗口"）③权限清单（AI 能替谁干、干到什么程度要问人） |
| 2 | **脚手架命令** | Android Studio 的"新建项目"模板 | 跑一条命令，自动生成接入骨架（带填空位和填写说明），不用从零发明 |
| 3 | **发布校验器** | 应用商店审核 | 声明填漏了不给上线，报错用人类语言告诉你缺什么、去哪补 |

这三样就是"系统与 App 的关系"落地后的样子：**引擎定格式，业务来填空**。谁也不用改谁的代码。

## 3. 业务系统"生下来"该怎么设计（这才是根）

模块不止四个，所以不按模块讲，按**设计律**讲——这类网站开工时就该这么设计。守了它，AI 是免费送的；不守，每个模块都要单独补课。

### 3.0 先把分工说死：AI 工具是谁的？

**调用 AI、弹确认卡、审计、执行——全是 AI 办公室（引擎）的功能，业务系统一辈子不写这类代码。** 业务系统只出两样：功能本体（服务层的业务函数）+ 一份声明表。"AI 工具"诞生在交点上：

> **AI 工具 = 业务函数（业务系统写的，人用页面调的也是它） × 声明表（业务系统填的） × 调用机制（引擎管的：注册→权限→确认→执行→回读→审计）**

整个栈长这样，**中间层全系统只有一个，就是引擎**：

```
┌────────────── AI 办公室引擎 ＝ 中间层 ──────────────┐
│  AI大脑 · 工具注册表/执行器 · 确认卡 · 审计账本 · 画布 │
└───────────┬────────────────────────┬──────────────┘
      按契约调用│                     读取│声明表
┌─────────────┴────────────┐   ┌───────┴────────────┐
│ 接入薄壳（把服务函数对上契约； │   │ 声明表（随代码进git）│
│ 新系统=纯填表，老系统=补课）  │   └────────────────────┘
│ 业务服务层（业务函数本体）    │    ← 业务系统（CPQ/人事培训…）
│ 数据层                     │
└───────────────────────────┘
```

业务系统**不要**自建第二层 AI 胶水——谁在自己系统里私接一条调 AI 的暗道，谁就是下一个事故源。这条护栏内核里已经有了（"应用只能声明，不能带自己的编排逻辑"）。

### 3.1 五条设计律（开工时就守，和 AI 无关，守了 AI 免费）

为什么叫"AI 时代的设计"？因为一个网站历来有三类用户：①人+浏览器（所以页面要好看）；②人+手机（所以要 API——当年没留 API 的公司，移动浪潮一来被迫重写）；③**现在多了第三类用户：AI 智能体。它要的和手机 App 要的是同一层东西——干净的结构化服务接口。** 所以"为 AI 设计"没有新增什么接口类型，它检验的是你分层分得好不好。

| 律 | 内容 | 不守的下场 |
|---|---|---|
| 一、页面薄、服务厚 | 每个业务操作是服务层一个有名有姓的函数，页面只显示和转发 | 逻辑藏在按钮点击里 → AI 调不了，人也复用不了、测不了 |
| 二、操作三件套 | 每个函数：结构化入参出参、权限检查写在函数里、写操作可安全重试 | AI 调到"半截函数"（要靠页面状态补参数）＝事故 |
| 三、写完能查 | 写操作返回主键/单据号，能反查结果 | AI 说"提交成功"无法核实——写后回读就没法做 |
| 四、操作留痕 | 谁、何时、改了什么有记录（审计字段或操作日志） | 企业场景"谁干的"答不上来＝没人敢给 AI 开权限 |
| 五、声明随代码走 | 一份清单文件列"本系统开放给 AI 的操作/页面/权限"，跟代码一起进 git、一起改 | 声明靠口口相传 → 漏登记乱登记，引擎和业务对不上账 |

这五条就是"留什么接口"的完整答案：**不新增接口类型，就是把服务层做干净，再多一份声明文件。**

### 3.2 用你的四个模块验证（举例不止这四个，任何模块都套同一套律）

| 模块（举例） | 它本来就该有的服务函数 | 引擎替它做的事 |
|---|---|---|
| 线索页·线索登记 | 登记线索()、改派()、状态流转() | 交给 AI 时自动弹确认卡、记审计 |
| 商机详情·四步报价 | 落位成本表()、提交转报价()、加价()、出件()——交付工作流已经在调它们 | 写后回读核对、画布亮灯、审计回放 |
| 配件页·配件价格 | 查价()（读）、调价()（写+阈值） | 查价免确认、调价弹卡、超阈值转人批 |
| 解决方案·各类规则 | 读规则()（只读） | 规则对 AI 是法律：只能遵守不能改，改规则的永远是人 |

CPQ 后端本来就是 页面 → API → services → 数据库 的分层（`delivery_core` 就是"页面和 AI 同源同路由"的模范），所以**要补的不是 AI，是两件收编活**：①把散装手写的工具规格收编成第五律说的声明表；②个别只在页面/画布里存在的能力（如流保存校验）补出服务出口。规则那条多一条纪律：规则改动要过"行为基线考卷"（§6 第 5 步）。

## 4. 将来新建"人事培训系统"，怎么接到引擎上？

这就是你问的"又该怎么做"。假设引擎的三样东西（§2）已经就绪——也就是本方案第 1、3 步做完之后——**新系统接入是这么个过程。** 另外分两种情况：**新**系统从第一天就按 §3.1 的五条设计律建，接入是纯填表（下面这份清单）；**老**系统先把页面里藏的业务逻辑搬到服务函数（一次性补课），再填表。

> **比喻：入驻商场。** 商场（引擎）已经建好了水电、收银台、消防、保安、物业规章（运行时、确认卡、审计、校验器）。新商家（人事培训系统）入驻只需要：签入驻合同（填接入声明）、装修自己的铺面（自己的页面和业务逻辑）、把自家会员卡对上商场收银台（注册工具）。商家**不需要自己修商场的走道，也不需要懂商场的电闸**。

具体到人事培训系统，全部动作大概一周：

| 天 | 干什么 | 举例（人事培训语境） |
|---|---|---|
| 第 1 天 | 跑脚手架命令，生成接入骨架 | 一条命令，得到带填空位的骨架文件 |
| 第 1~2 天 | **填工具清单** | `查课程表`（读，免确认）、`帮员工报名培训`（写，要确认）、`发培训证书`（写，超 10 人转 HR 批） |
| 第 2~3 天 | **填页面清单** | 课表页注册为"排课结果"的产物窗口——AI 排完课，点开产物看到的就是那张真课表 |
| 第 3 天 | **填权限清单** | AI 能替员工报名（限额 N 人/次）；请假审批永远转 HR，AI 只能代查状态 |
| 第 3~4 天 | 过发布校验器 | 漏填会被人话报错拦住，照着补就行 |
| 第 4~5 天 | 试运行一条假流程 | 在画布上看：每步输出物非空、确认卡正常弹 |
| 第 5 天 | 上线 | 之后在公司 AI 办公室说"帮新员工排入职培训"，AI 就能真排进课表 |

**这七天里没有任何一步在改引擎代码。** 这也是检验本方案第 1~5 步做没做好的标准：这个七天清单将来跑得顺不顺。

## 6. 改造分六步走（v2）

> **v2 修订缘起（2026-10-31）**：需求分析实测暴露三个问题——①趋势/交付的节点产出物缺失或只有长子规整 ②AI 问完不弹选项卡、4 秒后自行代答落定 ③各流产出物形状不一。分析定案：三个问题是**两个缺失原语**的症状——**产物契约按域注册**（builder 七槽全是需求分析域私产）和**决策闸**（多候选无用户信号没有机制闸，问询存在性押在大脑自觉上）。按原语吸收进路线图，不打补丁。

每个步骤做完，系统照常能用、可回滚；步骤内部再细分小段，一次只开一段。

| 步骤 | 干什么（人话） | 做完你会看到什么 | 怎么验收 | 大概工作量 |
|---|---|---|---|---|
| **第 1 步：立规矩**（已落地，收尾中） | 把"一条工作流必须带什么"写成清单，并让机器把守：保存工作流时漏填就拦（报错说人话）；"输出物种类清单"后端单源、前端来取。+ 增补：校验条款扩展——input/output 节点的产物契约、决策点声明纳入检查（本次实测暴露的盲区） | 新建/保存工作流时，漏了目标层、规则这类东西会被当场拦下，报错告诉你缺什么；AI 想漏都漏不了 | 用户真机验收（三条流可见、画布可开、抽屉三区非空）→ 切 enforce 硬闸 → 服务器库点名补种子 | 收尾中 |
| **第 2 步：决策闸**（v2 新增） | 给引擎添第四个闸：节点契约新增**决策点声明**（哪个节点要用户拍板、选项=库内候选自动生成、recommended 置首、Other 兜底）；引擎保证"声明了决策点 → 用户没拍板 → 发 choice 卡并停轮"；AI 只执行，**禁止代答**（实测事故：AI 列了 4 个 GPU 选项没弹卡，4 秒后自己选了个非推荐款落定出件） | 再遇到"库里多候选"类情况：选项卡必弹、AI 停下等你、你点了才继续——像 Claude 的提问一样，但由机制保证，不靠 AI 自觉 | 考卷场景：多候选流必须停轮发卡（库里有问询记录、无自行落定）；负向：AI 绕过声明自行填槽 → 引擎拦截出件 | 1 个迭代 |
| **第 3 步：发模板**（原第 2 步 + 产物契约域化） | 提供"新建工作流"的脚手架命令和画布向导（填空式）；抽屉五件套从"需求分析专用"搬出成公共件；+ **产物契约域化**：给趋势补输入（用户问题原文）/输出（趋势结论结构化）的产物 builder 和渲染组件，交付流节点摘要规整度对齐——"模板 = 结构 + 产物契约 + 决策点声明 + 左栏规则"的全套 | 每条流的节点产出物都能点开、都规整——不再"长子有、其他没有"；搭第四条工作流 = 跑一条命令 + 画布填空 + 保存 | 用模板生成演练流：试运行全程每个节点的抽屉三区非空、产物可点开；趋势输入/输出可查看 | 1.5~2 个迭代 |
| **第 4 步：上安全带**（原第 3 步） | ①每个工具声明清楚"读还是写、要不要确认、权限要求"（对齐业界 MCP 标准）；②确认分级（查价免卡、调价要卡、大额转人）；③写后回读（AI 说干完了必须查过库）；④审计账本（每笔 AI 写库可回放：哪回合、哪个工具、改了哪行、谁批的） | 确认卡变少但更准；AI 报价单的价格能核对到配件库真实条目；出事能回放追责 | 跑一次完整交付流：数卡数（变少）、点开产物核对价格来源、在审计账本回放全过程 | 2~3 个迭代 |
| **第 5 步：养考官**（原第 4 步 + 新考题） | 给每条老工作流出一份"考卷"（固定输入 → 检查结构事实：跑了哪些步、落了哪些表、弹了几张卡），改规则/改提示词必须先考一遍。+ 新考题全部来自 10-30 实测：**多候选必停轮发卡（有问询、无自答）、节点产物非空、抽屉三区非空** | 这次的三个 bug 以后靠考卷拦，同类问题不再靠人工实测；改规则从"改完真脑试"变成"考卷先判、真脑复核" | 故意改坏一条规则 → 考卷红；改回 → 绿 | 1~1.5 个迭代 |
| **第 6 步：验独立**（原第 5 步） | 选第二个业务场景（如售后单处理），用模板搭第二条事务工作流，探针从写代码降级成填表；最后写一个"假宿主"演示——引擎不带任何 CPQ 代码跑通一条完整流。第二应用落地时，决策闸与产物契约被第二个域复用一次，再抽 DSL | **亲眼看到"引擎独立"**：一个假系统接入引擎跑通了全流程。到这一步，"AI 办公室独立出去"就不再是口号，而是复制目录 + 给新业务填声明 | 假宿主演练全链通过（这是给"独立"的第一次眼见为实） | 2~3 个迭代 |

### 路线图 v3（2026-10-31 战略复盘版）：从"CPQ 强壮"到"引擎独立"的剩余五步

v2 六步走的前半程解决的是"CPQ 里的引擎没规矩"；复盘问的问题是：**照最终目标，现在到底走到哪了？** 把终局翻译成四条可证伪的判定标准：

| # | 终点判定标准 | 怎么证伪 |
|---|---|---|
| S1 | 新接一个业务域，**只写声明、不改引擎** | 第二个域接入时动了引擎代码=不成立 |
| S2 | 代码里**画得出一条线**：这边是引擎、那边是业务（import 有方向） | 画不出这条线="引擎"只是说法 |
| S3 | AI 触达**业务的全部写面**：每个写操作要么有契约+确认+回读，要么明确声明"AI 不碰" | 有写操作没人管=目标②没完成 |
| S4 | 换个假宿主引擎照样活（L2） | stub 宿主跑不通=机制里藏着 CPQ |

照镜子结果：S1 有一个真证据（趋势流纯配置接入）但没考过"新形状的域"；**S2 不成立**（引擎模块与 CPQ 业务同住 `app/services` 互 import，如引擎侧 `skill_tools_write` 直接 import 业务侧 `delivery_core`）；**S3 ≈6%**（业务写面约 216 个端点，AI 有契约写工具 13 个——机制验证了，扩展路径还没有）；S4 未考（宿主接口只有一个样本，且内核埋着 `price_ok`/`colleague` 这类 CPQ 词汇）。

由此剩余路线图重排为五步，每步都明码标价还哪条标准的债：

| 步 | 干什么 | 还哪条标准的债 | 状态 |
|---|---|---|---|
| **第 4 步：上安全带（收尾，瘦身版）** | 直达执行路径审计补点——用户在确认卡点「确认执行」后系统直调工具、绕过 registry 统一收尾，**恰恰是最需要留痕的写没账**（`transaction_turn._execute_pending`）；顺带把两个已知既有测试失败 xfail 挂账。账本前端视图（GovernancePanel）降级为可选——不还终局的债 | S3 | 第一批已落地，收尾中 |
| **第 5 步：画边界**（提前自原第 6 步） | 一份"引擎模块清单"声明 + import 方向守卫测试（引擎不得 import 业务模块，业务可以 import 引擎）——把 S2 从叙事变成法律。先 report 模式看清单，违规解耦（改回调/注入）后再 enforce | S2 | 未开工（一天级） |
| **第 6 步：养考官**（原第 5 步） | 三条流行为基线夹具 + 新考题（多候选必停轮发卡、节点产物非空、抽屉三区非空）。**基线=引擎的行为规格**，是第 5 步解耦重构和第 8 步一切动作的安全网 | S1 的证伪装置 | 未开工 |
| **第 7 步：工具声明面**（新增，ABI 第五册） | APP 声明自己的工具清单（操作+读写+确认级别+回读函数）→ 引擎消费注册；现有 13 个手写工具迁成声明式作首样本。**这是 216 写面能摸平的唯一可扩展路径**——引擎替业务手写 dict 永远摸不平 | S3 的扩展路径 | 未开工 |
| **第 8 步：APP#2 验独立**（原第 6 步，场景已拍板） | **合同/订单审批流**——刻意选了形状不同的：审批链、通知、状态流转，专考内核缺什么原语。产出：宿主接口第二个样本（修正 `TransactionApp` 单样本猜测）、CPQ 词汇出内核清单、stub 宿主演练（L2 眼见为实） | S1+S4 终极证伪 | 场景已拍板，未开工 |

**终局标志**：S1~S4 全部可证伪地成立（L3 独立部署维持缓存不变）。真实的人事培训系统接入是终局之后的事，第 8 步的 stub 宿主先替它把路趟平。

> 说明：第 4 步收尾 → 第 5 步画边界 → 第 6 步养考官的顺序是刻意安排的——先还目标②最急的账（直达路径无账），再立法律（边界），立完法律马上养考官，**考官就位之前不做大的边界解耦重构**（没有安全网的拆焊是事故源）。

### 问题 → 步骤映射（10-30 实测三问题，全部被路线图按原语吸收，无补丁）

| 实测问题 | 缺失原语 | 归属步骤 |
|---|---|---|
| 趋势/交付节点产出缺失，只有需求分析能看 | 产物契约按域注册（builder 七槽全是需求分析域私产；需求分析的产出是引擎内建供给的） | 第 3 步（域化）+ 第 1 步（校验纳检） |
| 产出物规整度只有需求分析有（线索登记表逐字段 vs 别家摘要文本） | 同上——规整 = 结构化 builder + 专属渲染组件，其他域没有等价物 | 第 3 步 |
| AI 问完不弹卡、4 秒后自行代答落定（库里实锤：零问询卡，问询后 4 秒出件） | 决策闸（多候选无用户信号没有机制闸；调和器只管工具闸记录，内容性问询不在雷达内） | 第 2 步 + 第 5 步（考题） |

### 待你拍板的三个设计点（第 2 步动工前）

1. **决策点声明放哪**：建议放流节点配置（画布抽屉加"决策点"区：问什么、选项来源=库内候选自动、推荐标记）——配置者定语义，引擎保执行，符合"范式留 APP、机制进内核"。
2. **"用户没拍板"怎么判定**：建议 = 该决策槽位上没有用户点选/输入过的问询答案记录（AI 自己填的不算）——机制可查，不猜意图。
3. **AI 代答违约怎么处置**：建议 = 拦截出件并如实报错（决策类违约 = 跳过了用户，出件不可信）；备选是强制重调一轮。

### 已替你做主的最优选择（有异议随时推翻）

1. **不建重型拖拽编排器。** 画布保持现在的"看拓扑 + 抽屉改配置 + 试运行"，新建工作流走模板填空。依据：OpenAI 的拖拽编排器一年就停运了（§5 反面教材）。
2. **"独立"只做前两级。** 一级=引擎和 CPQ 的代码依赖方向守干净（机器把守）；二级=换个假宿主能跑通（演示验收）。"独立部署成单独服务"暂不做——单机单系统没有收益，等真有第二个系统要接再说。
3. **免确认白名单从严。** 初期只有"查库读数"类零风险工具免卡，其余全部保留确认。
4. **删掉 `slots_backfill.py`。** 这个文件建了 8 个月没有任何地方调用（我查过全后端零引用），挂着只会误导以后搭流的人。git 里有历史，真需要时按新规矩重建。（已于 10-30 执行）
5. **决策闸复用现成问答协议**（choice 型卡、recommended 置首、Other 兜底），不新建卡种类——协议基建 10-23 已建好，决策闸只是给它接上机制闸和停轮语义。

## 7. 名词小词典（看工程版或跟 AI 讨论时对照用）

| 词 | 人话 |
|---|---|
| 引擎 / 内核 | 系统层，安卓系统的对应物。管推进、弹卡、审计、校验，不认识任何具体业务 |
| 宿主 / App | 接入引擎的业务系统。CPQ 是第一个，人事培训系统可以是第二个 |
| 工具契约 / ABI / 接入声明 | 一个东西的三种叫法。就是 AndroidManifest：声明工具、页面、权限 |
| 工具 | 业务系统提供给 AI 的标准操作（如"查配件价"），每个标注读/写、要不要确认 |
| 探针 | "这步活干完没"的查库问题（如"报价单落库了吗"），AI 说了不算，查库说了算 |
| 案台 | AI 每轮开工前看的"工作台现状快照"，从真实表现算出来，不信 AI 自己上轮说的话 |
| 调和器 | 保证"该弹的卡一定弹、最多弹一张"的状态机（10-23 已建成） |
| 探针 DSL | 把"写代码声明探针"降级成"填表声明探针"，让第三个工作流起加流更省 |
| 接入包 / host adapter | 新系统接入时写的那份注册代码，类比入驻合同 |
| 独立三级 | L1 代码分干净 → L2 换个假宿主能跑 → L3 单独部署（第三级暂不做） |
| 行为基线 | 给 AI 行为出的考卷：固定输入，检查结构事实，改规则先考一遍 |
| 写后回读 | AI 执行写操作后当场查库核对，"已提交"必须查过库才能说 |
| 确认分级 | 查价免卡、调价要卡、大额转人——分诊，不是一刀切全弹卡 |
| 决策闸 | 库里有多个候选、用户没拍板时，引擎自动发选项卡并停轮——AI 只执行不代答（第四个闸：缺口闸/确认闸/问答协议之后） |
| 产物契约域化 | 每个业务域给自己的节点注册"产出物长什么样、怎么渲染"——不再只有需求分析域有 |
