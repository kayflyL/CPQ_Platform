服务器选型配置涉及的不只是文字规则，还包括：

- 约束关系：某些配件不能同时选择。
    
- 依赖关系：选择某个配件后，必须增加或更换其他配件。
    
- 计算关系：根据 GPU 数量、功耗、内存容量等推导其他配置。
    
- 兼容性关系：CPU、内存、硬盘、网卡、Riser 等必须满足平台兼容性。
    
- 优先级关系：多个配置都满足需求时，应该优先选择哪一种。

### 2. 没有区分 AI 理解需求和规则执行

原文给人的感觉是：

把规则告诉 AI → AI 理解需求 → AI 选择服务器 → AI 选择配件 → AI 组装方案。

但实际上，这里面至少有两种不同性质的工作：

|工作类型|具体任务|更适合的实现方式|
|---|---|---|
|需求理解|理解客户场景、性能需求、预算及约束条件|LLM|
|服务器选型|根据需求匹配产品目录|LLM + 规则|
|配件选配|根据平台、接口、规格及依赖关系选择配件|规则引擎 + 数据|
|配置组装|形成完整 BOM 配置方案|程序化组装|
|方案校验|检查兼容性、完整性及需求满足情况|规则校验 + LLM 辅助|

这里有一个很重要的观点：

AI 不应该只是一个按照文字规则工作的配置员，而应该是一个能够理解需求、调用专业能力、协调不同工具完成任务的方案助手。

这也是 Workflow 存在的意义。

### 3. 忽略了需求不完整时的处理

人工做服务器方案时，并不是拿到客户需求就直接开始选型。

经常会遇到：

- 客户没有明确 CPU 核心数。
    
- 只提出 GPU 型号，没有明确数量。
    
- 只描述业务场景，没有明确性能指标。
    
- 预算与实际配置需求存在冲突。
    
- 需求中存在相互矛盾的条件。
    

这时需要反问客户、补充需求，或者在明确假设的前提下提供方案。

因此，需求理解和需求分析不应该只是简单的信息提取，还需要包含需求缺口识别、澄清和约束判断。

### 4. 缺少最终验证环节

这是我认为最值得补充的一点。

AI 生成了一套配置，不代表这套配置就能交付。

至少需要验证：

- 配件之间是否兼容？
    
- 机箱槽位和接口是否满足要求？
    
- 电源、散热是否满足整机需求？
    
- BOM 是否完整？
    
- 是否真正满足客户的性能需求？
    

所以，工作流不应该以「组装配置方案」结束，而应该以「校验并输出可用方案」结束。
