# 交付工作流方案(终版):成本表/方案表 → 报价单

> 状态:方案定稿待执行。原型:`docs/prototypes/交付工作流-原型.html`(形态对齐 SkillStudio 三栏)。
> 最后更新:2026-10-17

## 1. 背景与问题本质

写操作工具/上传/确认机制已在聊天侧验证(真脑E2E四轮)。把交付链改造成工作流后的真脑实测暴露了根本问题:

**workflow 会话每回合在未绑定商机时,经 `_ensure_ai_office_opportunity` 创建一个轮换的隐藏 `ai-*` 载体商机**(名字=当轮回复片段)。这是需求分析的范式——她的四步表单需要"沙箱载体→转真实商机"的生命周期;但该机制被写成了**所有工作流会话的无条件行为**。交付链(要落在用户确认的真实商机上)被轮换假商机打断:落位/提交/加价全打在假载体上,最终回复与已完成的工作自相矛盾。

次要问题(同根):自由大脑扛全链的模型波动(编造客户名/漏填登记)——已由确认卡机制与先看后落顺序缓解,工作流化后由确定性节点根除。

## 2. 范式对齐(与现有工作流完全同构,零新概念)

解剖现状:画布 `reasoning_flow.graph` = **纯拓扑**(节点 `{id,type,label,position,runtime}`,需求分析6节点/趋势3节点);节点行为在**配置面**(capability_spec 默认 + `reasoning_node_config` 覆盖 + 左栏使用说明);大脑行为规则的**唯一出处 = 左栏 manual_rules**(需求分析=1260字24条编号任务规则,C1)。

交付工作流**只使用既有节点类型**,确定性靠"单工具白名单 + 引擎硬校验顺序 + 左栏规则":

| 画布节点(类型) | 白名单工具 | 左栏规则要点 |
|---|---|---|
| 接收识别(input) | import_cost_sheet(analysis)+ query_data | 先解析;按表自述转述;分流按分流表配置 |
| 商机定位/建档(agent) | create_opportunity | 客户名以用户最新说法逐字为准;缺归属先问 |
| 线索登记回填(agent_fill) | save_requirement_draft | 解析值自动回填标来源;缺口一次一卡;已知悉豁免 |
| 落位(compose) | import_cost_sheet(落草稿)/ bom_scheme_draft | 成本表→成本桶+最小方案;方案表→boming 桶 |
| 提交推进(agent) | submit_cost_sheet | 预览原样转述;确认才执行;已提交不重复 |
| 加价(agent) | set_quote_margin | 口径问用户;换算由核心层完成禁心算 |
| 出件(output) | share_quote(artifact-share 文件型) | 默认 internal;customer 走外发审批闸 |

## 3. 会话实体绑定(长期修复:硬编码机制 → skill 声明的能力数据)

**问题本质**:载体创建是需求分析的范式(沙箱→晋升),却被写成了所有工作流会话的无条件行为。长期修复不是打补丁,是把"会话挂什么实体"升级为 **skill 声明的策略**:

| 策略 | 语义 | 适用 | 行为变化 |
|---|---|---|---|
| `sandbox` | 隐藏 `ai-*` 载体,登记落定后晋升 | 需求分析 | **零变化** |
| `real_bound` | 绑定真实 active 商机;时机=确认卡(用户确认客户名/归属那一刻,核心层建档或解析既有) | 交付转报价 | 轮换载体不复存在 |
| `none` | 不挂商机 | 趋势分析等 | 顺带治愈其现状浪费 |

**机制改造**(`session_entity.py` 公共件,唯一实现):声明读取(skill 条目)+ 绑定读写(会话状态)+ 节点解析;`colleague_turn_io` 的调用点按声明分发。**迁移零破坏**:需求分析=sandbox(逐字现状);趋势=none。

**验收**:①需求分析 E2E 全绿(沙箱路径零变化);②交付 E2E 断言全程 `ai-*` 载体创建数=0、绑定后所有节点写同一真实商机;③趋势无载体创建。

## 4. 入口分流表(扩展点:新表 = 加一行)

| 工件类型 | 识别 | 落位 | 自动回填 | 跳过 | 下游 |
|---|---|---|---|---|---|
| 成本表 | 意图+结构试解析 | 成本草稿(costing桶) | 机型/数量→需求槽位 | boming(自动生成最小方案) | 提交→加价→出件 |
| 方案表 | 意图+L6/配置行结构 | BOM 方案草稿(boming桶) | 配置行→方案 configs | —(成本=库价推导或等成本表) | 成本→提交→加价→出件 |
| 未来新表 | … | 新增落位分支 | … | … | 共享下游 |

**工作流数量按业务交付物划分,不按文件类型。** 需求分析保持独立(选型推理管道)。

## 5. 输出物 / 节点产物契约(对齐《节点产物契约》四原则)

四原则:每节点只写自己的真实表;输出物=对应节点的真实业务表(唯一份);字段权威=真实表 schema;换插头=换让 AI 填另一张真实表。

| 节点 | 写哪张真实表(唯一份) | 下游谁读 | 写回上游 |
|---|---|---|---|
| 接收识别 | (无表,运行时解析摘要) | 建档/落位 | 否 |
| 商机定位/建档 | `opportunities`(建档路由) | 全部下游 | 否 |
| 线索登记回填 | 线索登记表(`requirement_slots`,落定即冻结) | 下游只读 | 否 |
| 成本落位 | `opportunity_cost_sheets`+附件桶(成本核算) | N4 | 否 |
| BOM 落位 | `opportunity_bom_schemes`+附件桶(BOM方案) | N4 | 否 |
| 最小方案 | `opportunity_bom_schemes`(current) | 提交前置 | 否 |
| 提交推进 | `quotations`+`quotation_items`(影子建单+convert)+流程推进 | 报价工作台 | 否 |
| 加价 | `quotations`/`quotation_items`(工作台同口径重算) | 报价工作台 | 否 |
| 出件 | 附件桶(报价单 xlsx)+分享 token | 客户/内部 | 否 |

解析摘要为运行时对象不落库。产物两类:落库型(业务页面查看)+ 出件文件型(artifact-share)。

**验收(出件前终检)**:配置数与原表一致、金额=工作台同口径重算、口径与用户选择一致、流程节点到位——任一不符=暂停并如实说明。

**实现影响点**:output 节点 kind 白名单现状只认 requirement_draft/bom_scheme_draft → 出件走文件型产物(artifact-share 既有管线,零新渲染),白名单不动。

## 6. 行为规则:左栏任务规则(唯一出处,C1)

交付工作流的 manual_rules(左栏,编号任务规则)承载大脑全部行为纪律——**工具结果里不写指令,只摆事实**(C1 修正已落地:instruction/fixation_hint 类文案已从工具结果剥离,规则住提示词/左栏):

```
1.【先看后落】工件先解析预览(零落库),把识别结果按表自述复述;商机未指明→带推断确认
  (客户名以用户最新说法逐字为准,文件名只作推断依据)。
2.【一次一卡】缺口与确认一律一卡一项;用户已点选→先确认收到再转下项;拒绝或改参数→预览处终止。
3.【商机】客户名逐字取用户最新说法;预览原样展示客户名与归属业务;缺归属业务先问再建。
4.【登记回填】解析值按槽位契约自动回填标来源;缺口一次一卡;已知悉豁免;落定即冻结,下游只读。
5.【落位】成本表→成本核算桶+成本草稿(同名原地更新);方案表→BOM方案桶。原件必归档。
6.【提交】需 current 方案(缺→由成本行自动生成最小方案);确认卡通过才执行;已提交不重复。
7.【加价】口径问用户(加价率/利润率),换算由工具完成禁心算;预览改前改后确认才写库;
  外发审批中锁价如实转告。
8.【出件】默认 internal;customer 视角走外发审批闸不代办;时效/可撤销如实说明。
9.【收尾】每节点完成同步库内状态复述;全链结束汇总产物清单。
```

工具结果只摆事实(如 `overrides_applied`、`analysis_only`、缺失槽位清单)——大脑依据左栏规则决定如何利用。

## 11. 落地记录(2026-10-18):事务执行器接线 + 全链真脑 E2E 走通

**架构定案(案台原则)**:需求分析引擎的状态通道是线索登记表(slots),交付链产物在那是
没有座位的——事务管道自己的案台=每轮从业务真实表现算现状(不信任叙事),步骤指针=
流节点序里第一个产物未落者。判断全在大脑,顺序在指针,状态在库。

- `delivery_executor.py`:案台视图(state_view:商机/成本表/报价单/暂存附件/待确认/旗标)、
  步骤指针(_STEP_PROBES 按流节点键)、digest(纯事实块,C1)、apply_facts(工具事实→状态槽
  旗标:加价/分享)。步骤配置权威源=DB 流节点(顺序/标签/工具白名单/左栏规则)。
- `delivery_turn.py`(新模块,布局守卫已登记):`_run_delivery_chat` 聊天轮外壳——每轮
  现算案台→指针停哪步大脑带哪步工具白名单干活→产物落了指针前移续跑(每回合≤4步),
  没落(反问/等确认/答疑)停在本步等用户;`dispatch_flow_turn` 按实体绑定分发
  (real_bound→交付执行器,其余→需求分析引擎),服务层三处调用点统一走它。
- 状态槽:线程 reasoning_state key=`delivery_flow:{role_key}`,只存探针查不到的旗标
  (加价已执行/分享已出);装填时干净重开连状态槽一起清。
- **E2E 实测**:真脑全链 169.9s/4 回合走通(解析预览→建档+落草稿+提交预览→提交执行
  +加价预览→加价执行+出件),每道闸机械生效,测试数据全清。
- **机制堵洞(set_quote_margin)**:confirm 分支原先不过确认闸,大脑 momentum 直呼
  confirm=true 可绕过预览直接执行——已改与 submit 同形(先消费待确认记录才执行),
  回归测试 test_set_quote_margin_confirm_first_call_rejected_without_preview。

  注册表 resolve_app、状态槽、案台组装、指针推进、事实回写全部通用——内核不认识任何具体业务。

  fresh=True(装填)=干净重开连状态槽一起清。

  防"每个应用一套小操作系统"回潮。**新事务工作流 = 种一个流 + 写核心函数 + 一个 App 声明注册。**
