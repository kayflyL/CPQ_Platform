# 工作流（Workflow）：为什么做、怎么做、做到了什么

> 本文双重身份：①对外讲解稿——把「我们为什么不走主流 Skill 路线、而是自建工作流引擎」讲清楚；②设计红线——后续任何 AI 参与设计/改造时，凡与本文「铁律速查」冲突的方案一律视为违背原始设计思路，须停下重新论证。
> 与代码现状的关系：机制细节以《[需求分析skill-技术架构.md](需求分析skill-技术架构.md)》（权威现状快照）为准，本文讲设计意图与道理，不重复机制清单。
> 最后更新：2026-11-03

---

## 0. 一句话

**我们的系统里，AI 不是自由发挥的聊天机器人，而是按排班表上班的员工：工作流是排班表和交接单，AI 是那个唯一的大脑，一步一步把需求变成能直接进报价的真实业务表。**

---

## 一、为什么做：业务要的是交付物，不是聊得好看

### 1.1 最初的需求：让 AI 学会做配置方案

这个功能的起点很朴素：我们想让 AI 生成服务器配置方案。人工做方案的过程是这样的——先理解客户需求，再根据性能要求和适配规则，从产品目录里选服务器、从配件库里选配件，组成一套配置方案。这个过程里最费神的两步，「理解需求」和「按规则选型」，恰恰是 AI 擅长的：选型规则相对明确、可以沉淀成文字。把配置规则告诉 AI，让它理解需求、从产品目录里选服务器、从配件库里选配件、组装配置方案——理论上完全跑得通。

### 1.2 但我们的产出是钱：AI 必须可控

真正动手时问题来了：服务器配置方案背后是真实物料、真实价格和真实业务规则，**错一行就是真金白银**。而客户需求的输入千变万化——一句话的需求、成页的需求清单、口语化的描述——都会影响 AI 的理解和发挥，进而影响最终产出物。落到几个具体的担心上：

- AI 会遵守配置规则吗？（提示词里写了「必须」，它就一定「必须」吗？）
- 会老老实实从配件库拿料，还是自己「编」一个不存在的型号？
- 会不会选了 AMD 平台的服务器，却给配上兆芯的 CPU？

这些担心靠提示词压不住——需要的是**确定性保障**：规则被违反时有人拦得住，物料必须来自真实库存，平台冲突根本落不了表。

### 1.3 那能不能通过 Skill 来完成呢？

行业里现在最热的形态是 Agent Skills（Anthropic 2025 年 10 月发布，后成为开放标准）：一个文件夹，装着说明书（SKILL.md）、脚本和资源，模型自己决定什么时候用、怎么用、用多久。参考：[Equipping agents for the real world with Agent Skills](https://www.anthropic.com/research/equipping-agents-for-the-real-world-with-agent-skills)。

Skill 的本质是「给模型发说明书」——它提升的是模型「会不会干某类活」，但不约束「怎么干、干到哪算完、产出物落到哪」。放到我们的场景里，让模型自由发挥有四个过不去的坎：

1. **不可预测**：模型自己决定走几步、先问什么后问什么，同一个需求两次跑出来路径不同；
2. **产物不可靠**：自由对话的产出是聊天文本，而我们要的是能被下游确定性消费的业务表——文本方案没法转报价；
3. **不可审计**：客户没明说的参数被模型「顺手定了」，出了问题查不出是谁在哪一步拍的板；
4. **延迟不可控**：开放循环没有边界，一次简单的需求登记跑 8 分钟，是我们实测发生过的。

这条路 Anthropic 自己也替我们排除过。《Building effective AI agents》把两条路线分得很清：**workflow 是用预定义代码路径编排 LLM，换来可预测性；agent 才是模型自己指挥自己的过程**，并明确建议「能用简单可组合的模式就别上自由 agent」。参考：[Building effective AI agents](https://www.anthropic.com/research/building-effective-agents)。

2026 年我们核查生产级案例时也得到同样的结论（微软 Conductor、Backbase、Kong 等团队的公开实践）：**确定性编排包裹 LLM，确定性引擎是唯一事实源，AI 只做推理和推荐**；让 LLM 接管整条配置流水线是被点名的反模式——上下文陷阱、不可检视、贵、幻觉规则。

### 1.4 结论：skill 让模型知道更多，工作流让业务产出更可靠

skill 形态解决的是「让模型知道更多」，我们需要的却是「让业务产出更可靠」——前者一份说明书就能做到，后者必须靠工作流。所以我们选工作流，不是保守，是和业界结论对齐：**把确定性给编排层，把智能给节点内的 AI**。

顺带回答「我们系统里为什么没有 skill」：早期做过「能力包（skill）」这一轨——给 AI 同事绑定能力说明。但想明白它的真实地位后，2026-09-26 定调下线：**能力包只是使用说明，不是任务流**——它能告诉同事「什么时候该用我」，干活必须落到一条真实的工作流上。管理面随之统一更名「工作流」（后端表名/路由作为历史命名保留，不再新增能力包轨）。

## 二、怎么做的：插头插座 + 唯一大脑 + 闸门

### 2.1 心智模型：AI 是唯一大脑，工作流只是指引

这是整个设计最重要的一句定调（2026-09-12 用户原文）：

> **AI 角色 = 唯一大脑。workflow 不是驱动器，是指引——告诉 AI 该走哪些步骤、每步输出什么给下游；步进闸门只是护栏，不决定怎么干。**

AI 是同一个「人」，先后扮演不同的业务角色：在登记节点是**线索登记员**，在选型节点是**方案配置技术员**。角色怎么换？**交接靠表**——上游把产物填进一张真实业务表，下游只认表、不认聊天里说过什么。这条是工作流的验收标准：如果下游依赖了聊天里独有的信息，那不是模型的错，是登记表漏了字段。

为什么强调「唯一大脑」？因为另一个方向——每个节点各养一个自治小 agent、agent 之间自己对话协作——就是业界点名的反模式：贵、不可检视、上下文会滚雪球。我们的节点内 AI 有工具、有推理循环，但**它的大脑只有一人，只是换工牌**。

### 2.2 功能架构：一条六节点链

需求分析工作流（`requirement_analysis`）的链路：

```
input（需求进入）
  → agent_fill（线索登记：AI 把需求填进登记表，缺什么问什么）
  → model_reason（机型选型：AI 从在售机型池里定机型）
  → kp_reason（配件选配：AI 按性能语义从配件库选件）
  → compose（BOM 组装：确定性拼接底座+配件，出方案配置）
  → output（交付：真实业务表 + 面向客户的收尾汇报）
```

支撑这条链的是四个机制（细节见权威架构文档，这里讲设计意图）：

**① 编排壳不认识任何节点。** 引擎（`skill_turn_engine`）只认注册表和闸门，代码里没有「如果是登记节点就……」的分支。新节点 = 写一个插件注册进来，引擎零改动。这是「树干稳定、枝叶生长」的代码体现。

**② 步进闸门。** 每步结束由闸门裁决：`advance`（目标表填好了，放行）/ `pause`（缺东西，弹确认卡问人）/ `deliver`（可以交付了）。最后还有一道终检（final_gate），产物不齐不许出门。**关键定调：校验失败的机制文案只回喂大脑，永远不出机制黑话给客户**——客户只看到有人话选项的确认卡。

**③ 状态分区与冻结文档。** 每个节点的中间状态是私有分区；上游产物对下游是只读快照，**写就报错**（越权检测）。登记表唯一写入者是登记节点，下游永不回填——这不是靠纪律，是靠代码抛异常。

**④ 产物 = 真实业务表的唯一一份。** 产物不是 AI 临时编的 JSON，而是商机详情页那张真实表本身。AI 路径写的就是人手填的同一张表（draft/current 版本化），这就是「AI 是配置器」的落地。

### 2.3 插头插座：机制住代码，内容住 DB

第二根定调柱子是存储与配置架构（2026-09-02 定调，五条铁律）：

- **同一份东西只存一处（单一权威源）**：提示词只在 DB（前端改 → DB → 后端只读，**无第三层**，代码里禁止存提示词常量、禁止「DB 空则代码兜底」）；规则统一在策略中心-需求分析；工具绑定在节点抽屉；业务数据在业务表。
- **树干-枝叶模型**：树干（代码）= 六节点编排、大脑回合、确定性校验/缺口协议、工具 registry、节点接口契约；枝叶（DB 数据）= 提示词/规则/工具绑定/数据源/目标层配置。枝叶可以慢慢补，树干不动。
- **节点五插槽接口**：①目标层（输出表 schema，即本节点要填的那张表）②AI 层指令 ③资源层绑定（数据源+工具）④执行机制声明（确定性 or 大脑回合）⑤上下游数据协议。
- **wiring 也 DB 化（2026-09-14）**：节点与引擎处理器的接线关系存 DB，配三道闸——启动期自检、保存期 400、运行期白盒告警。改接线不碰代码。

**验收标准只有一条：录一条规则 / 换一张目标表 / 换一个数据源，不碰代码生效。** 这个标准不是口号，被「第二台机器」实证过：趋势分析工作流（`trend_analysis`）是第一个复用这套插座的非需求分析流程，从「+」发起到 PDF 报告落会话，全程零需求分析专用代码——插上就通电。

### 2.4 我们创新了什么（相比其他产品的差异点)

对照市面上三类产品，我们的位置：

| 产品形态 | 节点是什么 | 我们的差异 |
|---|---|---|
| 可视化编排平台（Dify / Coze / n8n） | 静态函数节点 + 一个裸 LLM 提示框 | 我们的节点是**一个 AI 角色上岗干活**：有人设、有岗位手册（规则）、有工具箱、有要填的表；不是一次性 prompt 调用 |
| Agent Skills（Anthropic 开放标准） | 给通用助手发说明书，模型自决路径 | 我们的说明书是**节点化的**：每步有边界、有产物契约、有闸门验收；说明书改的是「怎么干好这一步」，不是「要不要开始」 |
| 自由多 agent 协作 | 多个 agent 互相派活 | 我们**只有一个大脑**换工牌，交接靠表——可控、可审计、可复现 |

具体到机制层，五条别人没有（或没做严）的东西：

**1. 表格即接口（目标层输出物插座）。** 每个节点声明「我给下游什么表」，抽屉里可视化配置；AI 的工具参数、提示词里的契约简报、前端确认卡，全部由目标层 schema 动态生成。**换一张目标表，AI 的行为跟着变——代码里没有业务字段清单**。这就是「插座」的字面意思：节点留的是接口，插什么表干什么活。

**2. 推断必确认。** 客户没明说、AI 推断出来的值，必须弹确认卡让人点头才能落表（推断值直接喂下游选型，错了整链跑偏）。有一个体面的豁免：客户明示「一切你定、按推荐来」时，不逐项烦人，折进一张「整体落定卡」一次确认——授权留痕不断，只是合并。这条豁免是被实测逼出来的：「否则系统一点智能性都没有了」。

**3. 引擎硬执行。** 提示词压不住模型的场景必须由引擎强制（实测教训：必填追问写成软提示，模型就服从「客户没说的留空」而不问）。必填策略、KP 必登记类目、交付闸门、数据口径核对，全是引擎弹卡/拦截，提示词只是第一道。

**4. 白名单接地。** AI 选机型只能从在售机型池里选（取值域只认候选池，池外一律拒绝并回显候选）；选配件按「类目+料号名」回库核对。AI 可以推理，但**落库的每个值都有出处**——不编料号、不编价格。

**5. 人机节奏向 Claude Code 看齐。** 一轮一问（先选一个，选完再弹下一个）、答案落槽（打字答一个词视同点选）、缺口一次问全的上限控制、「少说多做」的旁白预算。这套节奏是拿真实客户对话一轮轮磨出来的，不是设计出来的。

### 2.5 和确定性推理流的关系：两条路线，一个哲学

系统里还有一条**确定性推理流**（策略中心的可视化 DAG：选底座→匹配配件→组装→预算→审计→复核，图驱动 executor + 条件分支）。它和 AI 工作流不是竞争关系，而是同一哲学的两个档位：

- **确定性管道**处理规则明确的部分（底座推导、组装、算价、审计）；
- **AI 工作流节点**处理语言模糊、需要语义理解的部分（需求理解、语义选型）；
- 定调（2026-08-07，对标业界）：**确定性管道当编排器和事实源，agent 只做「推理增强的接地节点」；全自治 agent 吞掉整条流水线是反模式。**

## 三、预期效果：已经兑现的和正在长出来的

### 3.1 已兑现（有实测数据背书）

**① 输出方案配置，直接进报价链。** 需求分析工作流的最终产物就是商机详情页「方案配置」环节配置完成、待提交的那张真实配置表——不是聊天里的文本方案。下游确认后转草稿，接成本核算与报价单。等价验收标准一句话：**AI 跑完，等价于人工在方案配置页点提交前的状态。**

**② 输出标准格式的分析报告。** 趋势分析工作流已全链路生产可用：AI 办公室「+」发起 → 数据查询（口径工具单点）→ 七节报告 → 服务端渲染 PDF → 会话文件卡下载 + 任务看板可取。报告结构、数据范围窗口、统计口径全部是配置（目标层 document 插槽 + 规则），**改报告格式不用改代码**。数据窗口交给 AI 曾出过复读旧报告的事故，根治方案也成了通用教训：污染从输入进来的，就在入口确定性剔除；闸门降级为永不触发的保险丝。

**③ 可控的体验与延迟。** 实测基线（真实 HTTP+WS+LLM+库 的端到端）：标准场景 3 轮 2 卡约 100 秒收口；客户全权委托场景 2 轮 1 卡约 73 秒；延迟优化把全旅程从 471 秒根修到 368 秒（假等待、思考撞顶循环、检索结论蒸发三类根因）。纯 LLM 填表的关键字段命中经可靠性测试约 100%，**没有退回 regex**——这是「打地鼠停止」的实证。

**④ 第二台机器即插即用。** 趋势工作流复用全部插座零改动，证明接口做对了。这是五插槽架构的验收标准兑现：**复用成立，才是接口做对的证明。**

### 3.2 正在长出来的

- **更多「多步 + 要交付物」的业务**都能插上插座：成本核算自动化、交付报告、竞品/库存分析——只要能画成「节点链 + 每步一张表」，就是第三台机器的事。
- **需求原文多模态**（图片需求单 → 文字）：设计已定稿，识别结果走确认弹层，绝不自动提交——多模态也遵守「推断必确认」。
- **规则知识化注入**：规则从「求值摆桌」升级为「知识注入」（词典卡/原则卡），规则页为唯一编辑入口，影子校验永不代填。

### 3.3 给听众的一句话总结预期效果

> 客户说一句模糊的话，AI 问清楚该问的、查库配出真实方案、填进系统能直接转报价的表；管理员改一条规则、换一个数据源，不碰代码第二天生效；换个业务，插上插座就是一台新机器。

## 四、设计铁律速查（给 AI 的红线清单）

任何后续设计/改造，与下列任一条冲突即视为违背原始设计，须停下论证：

1. **单一权威源，无第三层。** 提示词只在 DB；规则只在策略中心；工具绑定只在节点抽屉。代码里禁止提示词常量、禁止「DB 空则代码兜底」、禁止新增默认值/词表/业务常量进代码（先问用户：这是业务事实还是技术常量）。
2. **AI = 唯一大脑，workflow = 指引。** 不引入第二大脑，不做节点间 agent 互派活；工作流只告诉 AI 走哪些步、每步交什么表。
3. **交接靠表。** 跨步骤信息必须进目标层产物（真实业务表），下游只读上游快照、永不回填；下游缺信息 = 登记表漏字段，不是模型错。
4. **推断必确认。** 系统推断的值必须弹卡确认（唯一豁免：客户明示全权委托 → 折进整体落定卡一次确认）。多模态识别结果同理。
5. **软提示压不住模型。** 必填/口径/边界类策略必须引擎硬执行（弹卡、拦截、闸门），提示词只作第一道。
6. **机制与内容分离。** 代码只留机制与接口；业务规则、话术、文案、口径一律进对应 DB 权威源。禁令式文字不进黑盒代码——代码只许形状陈述。
7. **编排壳不认识节点。** 新增分派逻辑按 output_kind/插座属性走通用分支，禁止往需求分析专用代码里加 if；兜底表宁空勿错（张冠李戴温床）。
8. **白名单接地。** AI 落库的取值必须能回库核对出处；候选池外拒绝代选。
9. **纯 LLM 填表，绝不退回 regex。** 新格式差异改提示词/规则，不加正则补丁；修 bug 同步清理关联冗余，别在补丁上打补丁。
10. **验收标准 = 不碰代码生效 + 复用成立。** 换目标表/换数据源/录规则要即时生效；新工作流复用插座要零需求专用代码。两者任一不成立，说明树干被枝叶污染了。
11. **产物出口纪律。** 客户只看人话确认卡，机制黑话只回喂大脑；凡让 AI 统计/执行口径的场景，先对齐页面口径再写规则，且必须有确定性闸门兜底。
12. **能力包（skill）轨已定调退役**，别再捡回来；历史命名（skill_catalog 等）保留不重命名。
