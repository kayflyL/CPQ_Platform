## 0. 三条改造线、八个 Phase

### 0.1 病根与总原则

病根（2026-10-30 会话核实）：表现层契约（节点抽屉的目标层/规则层、运行时输出物）全部住在 `frontend/src/views/admin/reasoning/`（目录名就叫"需求分析"）；输出 kind 硬编码在前端 `ReasoningNodeDrawer.vue` 的 `OUTPUT_KIND_OPTIONS`；后端 `upsert_graph` 只有 entity_binding 保留闸、无完备性校验。AI 搭新流只填引擎**要求**的，漏掉引擎**没要求但 UX 期待**的——单测测的是引擎力学，漏契约无人拦截，用户实测才发现。

总原则（全部继承自既有实践，不是新发明）：

| 原则 | 出处 |
|---|---|
| UI 事实的存在性由机制保证，大脑只读事实写判断，从不做"触发投影"的开关 | 10-23 调和器定论 R0-R4，本方案推广到全部契约 |
| 同一族故障的多个补丁 = 没写出定理；先收敛成状态机+不变量 | 10-23 凌晨定论 |
| 绞杀式迁移、严禁推倒重写、每步可运行可回滚 | Principles.md ①② |
| 页面代理总纲：**范式留 APP，原语进内核**（"操作商机详情页"是 CPQ 的范式，引擎只提供"产物=业务对象引用、动作=注册的路由函数"这类原语） | 10-22 用户定调 + 本方案 §1.3 |
| 行为规则能降维成协议不变量时就降维 | 10-23 问答协议定论 |

### 0.2 三条线

| 线 | 名称 | 一句话 | 对应 Phase |
|---|---|---|---|
| **A** | 引擎内核化（AI 办公室独立的地基） | 表现层契约+工具契约+校验器+依赖方向守卫进内核 | P0、P1、P7 |
| **B** | 工作流系统 APP 化 | 公共件拆家、脚手架填空式建流、探针 DSL——搭流像写 APP | P2、P6 |
| **C** | CPQ 的 AI 时代改造（第一个 APP 的样板） | 工具契约升级、**决策闸**、确认分级、写后回读、AI 代理边界、审计、行为回归 | **P1.5**、P3、P4、P5 |

依赖关系：

```
P0(基线) ──► P1(发布闸) ──► P1.5(决策闸) ──► P2(公共件+脚手架+产物域化) ──► P6(第二应用+DSL) ──► P7(独立打包)
                    └────────► P3(工具契约+回读) ──► P4(代理边界+审计) ──► P5(行为回归+新考题)
```

P1.5 时序前移到 P2 之前的理由：模板必须携带决策点声明——声明契约（P1.5）没定，模板（P2）就没东西可带；且决策闸是正在发生的正确性 bug（AI 代答用户决策），优先级高于开发效率类改造。

P1 之后 P2 与 P3 可并行（两条线不同人可分头做）；P7 收尾依赖 P6 的第二个样本。

### 0.3 "独立"的三级定义（先对齐词，再干活）

| 级别 | 含义 | 判据 | 本方案范围 |
|---|---|---|---|
| **L1 模块边界** | 引擎代码与 CPQ 业务代码依赖方向干净 | 守卫测试：引擎模块禁 import CPQ 业务模块 | P7 落地 |
| **L2 可换宿主** | 换一个业务系统（stub），引擎不改一行能跑通一条流 | stub host 演练通过 | P7 落地 |
| **L3 独立部署** | 独立进程/独立仓库/API 服务，跨系统调用 | 出现第二个真实宿主 | **明确不做**（见 §5.1） |

## 1. 线 A：引擎内核化

### 1.1 现状盘点

**已经是内核器官的（保留并文档化）**：
- 事务内核 `transaction_engine.py`：只认 `TransactionApp` 契约（探针/旗标/事实行），"内核不认识任何具体业务"；
- 事件协议：`pipeline_start / node_trace / pipeline_waiting / pipeline_paused / pipeline_done / error`（`colleague_turn_runners.py:417` 统一分发），10-21 定论"两台运行时共用前端表现，对齐点在事件协议，新运行时接入=补发三个事件"；
- 问答协议 `human_query.py`：一个契约（choice/form/consent）、两个发起者、id 路由（10-23）；
- 确认闸调和器：R0-R4 不变量（10-23）；
- 工具唯一注册表 `_TOOL_SPECS` + `tool_catalog()`（有 name/description/parameters/category/default_enabled，**缺副作用/确认/权限结构化字段**——P3 补）；
- launch 表单（`launch_form` 独立列 + 专用端点，10-24）——已经是通用底座的好苗子。

**还不是内核器官的（本线要收编）**：
- 节点表现层契约：目标层字段契约、规则层、输出 kind、node_trace 的 artifact 载荷——散在需求分析的组件实现与种子数据里，引擎无要求、保存无校验；
- 流的发布闸：`upsert_graph` 无完备性校验；
- 依赖方向：引擎文件里还混着 CPQ 业务 import（P7 守卫会扫出来）。

### 1.2 ABI 清单（P0 产出的文档骨架）

引擎 ABI = 四份清单，缺一不可：

1. **事件协议载荷表**：6 个事件各自必填/可选字段；node_trace 在 status=done 时必须携带 `artifact{kind, refs, summary}`；
2. **节点契约表**：按 node type 列必填配置——agent/agent_fill 必须有目标层字段契约（key/label/必填）或显式 `no_artifact:true`；output 节点 output_kind 必须在注册表；manual_rules 非空；节点 label 必填；
3. **工具契约表**：现有五字段 + P3 增补的 effects/destructive/idempotent/confirm_policy/required_permissions/target_entity；
4. **宿主接口表**：`TransactionApp` 声明面 + 流发布校验入口 + 产物渲染注册（kind → 宿主页面组件的映射，这是"页面代理"进内核的唯一形态——引擎只存映射，不认识组件）。

### 1.3 对"独立"的一个警示（外部情报）

OpenAI 的 Agent Builder（2025-10 发布的可视化拖拽编排器）**将于 2026-11-30 停运**（§6 参照 2）。头部产品收缩重型可视化编排作者工具，说明引擎的长期价值在**协议与机制**，不在画布的繁华。因此本方案明确：不建重型可视化 WorkflowStudio（M3 原计划里的"壳抽取"降格为 P2 的轻量新建向导）；SkillStudio 画布保持现在的形态（拓扑编辑 + 配置抽屉），这恰好是幸存的模式。

## 2. 线 B：工作流系统 APP 化

### 2.1 搭流形态的三步演进

| 阶段 | 搭一条新流 = | 现状/目标 |
|---|---|---|
| 今天 | 从零发明：AI 凭记忆+先例代码搭，漏契约靠用户实测发现 | 趋势分析返工实录 |

原 M3 目标"加新工作流零代码"靠 WorkflowStudio 壳。按 §1.3 调整为：**零代码 ≠ 重型可视化编排器**，而是"模板 + 表单向导 + 校验器"三件套（P2）。画布继续做它擅长的事（看拓扑、改配置、试运行），不做流程逻辑的拖拽编程。

## 3. 线 C：CPQ 的 AI 时代改造与接入方式

### 3.1 已达标项（用 AI 时代的语言命名，不需要重做）

| 业界术语 | 你们已有的实现 |
|---|---|
| Tool use with real systems | 工具直调 `delivery_core`——业务唯一实现，页面与 AI 同源同路由（AI 和人操作同一个系统） |
| Human-in-the-loop | 两段确认 + 调和器 R0-R4（卡的存在性由状态机保证） |
| Grounding / write verification | 案台原则——每轮从真实表现算现状，"AI 说的不算，表里的才算" |
| Facts, not instructions | C1——工具结果只摆事实，规则住左栏 |
| Structured ask | 问答协议 HumanQuery/HumanAnswer（对标 Claude AskUserQuestion） |

### 3.2 接入架构（目标态）

```
┌──────────────────── AI 办公室引擎（独立候选体）────────────────┐
│  运行时(事务内核/推理引擎)   事件协议(pipeline_*)   问答协议      │
│  工具注册表(契约+确认策略+权限)   发布校验器   审计   launch表单   │
│  画布公共层(SkillStudio)   产物渲染分发器(按kind注册表)   行为基线 │
└────────▲───────────────── host adapter（宿主接口）──────▲───────┘
         │ 注册                                            │ 回调
┌────────┴──────────── CPQ 宿主（第一个 APP）─────────────┴───────┐
│  业务工具包(delivery_core 按契约包装)   产物渲染映射(kind→页面组件)│
│  权限键目录(action.*)   实体模型(商机/报价…)   分流入口   探针声明 │
└────────────────────────────────────────────────────────────────┘
```

关键不变式：**引擎不认识"商机"**。CPQ 把商机作为实体模型 + 工具集 + 页面渲染映射注册进去。页面代理总纲在目标态的落位：产物渲染映射 = CPQ 注册"哪个 kind 用哪个页面组件原样承载"；动作 = 注册的路由函数。趋势分析这类非商机域的流，用同一接口注册自己的实体与渲染——这就是"范式留 APP、原语进内核"的工程含义。

### 3.3 缺口四项与 Phase 映射

| 缺口 | 现状 | Phase |
|---|---|---|
| 工具契约无机器可读副作用声明 | needs_confirmation 只是 description 文案（全表仅一处） | P3 |
| 写后回读非强制 | 回合粒度案台兜底，工具粒度无强制 | P3 |
| 无 AI 代理边界与结构化审计 | TOOL_CTX.user_id 账号级；日志审批面板是日志堆 | P4 |
| 行为改动无机器兜底 | 靠真脑实测 | P5 |

## 4. Phase 逐项展开（P0–P7）

> 每个 Phase 的验收分两类：**自动化**（AI 保证）与**用户验收**（真机/真脑由用户做，按测试分工惯例）。改后端的 Phase 执行时必查 worker 重启时间与 `/build-stale`。

### P0 基线固化：ABI v0 白皮书 + 契约快照测试（线A，约 1 个迭代）

**执行内容**：
1. 写 `docs/引擎ABI-v0.md`：按 §1.2 四份清单落文档，每份清单标注现状出处（哪个文件哪个函数是单源）；
2. 契约快照测试：对需求分析流与交付流各录一次试运行事件流作为 golden fixture，断言事件序列与载荷形状（字段增删即红）；
3. 把 fixture 与 ABI 文档互相引用（文档里每条契约链接到断言它的测试）。

**目标**：契约从"散在实现里"显性化为"文档+测试双载体"；后续任何改动先红后改。
**预计效果**：AI 改动破坏契约时单测先红——不再靠用户实测发现空抽屉一类事故。
**校验**：全量测试绿；两条流的 fixture 入库。
**用户验收**：通读 ABI v0（预计半小时），确认每条契约与预期一致——这份文档就是用户与 AI 之间的契约基准。
**风险与回滚**：无行为变化；回滚=删文档删测试。
**执行注记（2026-10-31 落地）**：①契约快照的 v1 形态=**构造器级键集快照**（`tests/test_event_contracts.py` 锁两台运行时的载荷键集）；方案原列的"真脑试运行 golden fixture"依赖录制环境与真脑成本，**移入 P2 补录项**（P2 的演练流试运行正好产出 fixture）。②文档↔测试互引为**文件级**（ABI 每节标注断言测试文件），条目级互引待 fixture 补录时细化。

### P1 发布闸：校验器 + 输出 kind 后端单源（线A，止血优先级最高）

**执行内容**：
1. 新建 `backend/app/services/flow_validation.py`：`validate_flow(flow) -> list[Issue]`，按 §1.2 节点契约表逐节点校验（缺目标层字段契约且未声明 no_artifact / output_kind 不在注册表 / manual_rules 为空 / label 缺失），Issue 带 `节点id + 缺什么 + 人话修法`；
2. 接入流保存端点：先跑一周**报告模式**（只记不改），存量三条流（需求分析/交付/趋势）的缺口补齐后（预计恰好把趋势分析这次漏的都补上），切**硬闸**（error 拒绝保存）；
3. 输出 kind 注册表后端单源：新建 `output_kinds.py`（kind → 渲染契约描述）+ `GET /api/flow/output-kinds`；前端 `ReasoningNodeDrawer.vue` 的 `OUTPUT_KIND_OPTIONS` 改为拉接口；`NodeArtifactModal.vue` 按 kind 注册表分发渲染（学 HumanQueryCard 的 schema 驱动单渲染器）。

**目标**：漏契约 = 无法发布，而不是用户发现空抽屉；报错本身成为搭流 AI 的实时教学。
**预计效果**：第四个流起，搭流漏契约率趋零（以校验器拦截次数为度量）；趋势分析类的空抽屉事故从根上消失。
**校验（自动化）**：①负向用例：删掉交付流某节点的目标层字段 → 保存被拒且报错指明节点与缺项；②存量三流硬闸下通过（回归）；③前端 kind 选项与后端注册表一致性测试。
**用户验收**：画布上故意清空一个节点目标层字段 → 保存得到人话报错；三条约有流试运行输出物照常可点开。
**风险与回滚**：存量流过不了新校验 → 报告模式过渡一周；校验器留功能开关，回滚=关闸。
**执行注记（2026-10-31 落地+终验）**：①enforce 已生效（start_backend.bat 与 一键启动.bat **两处**注入——一键启动直起 uvicorn 不走 start_backend.bat，首轮漏了一处）；②负向 PUT 实测 **400** 带条款码人话报错、写前拦截配置零破坏；③E6 条款双路径执法（validate_flow+validate_node——首轮负向实测发现**单节点保存路径漏执法**，已修）；④**尾巴三项挪记**：(a) `no_artifact` 显式豁免通道未实现（W1 现为无条件 warning）；(b) output_kind 注册表纳检条款未加（output_kind 是 skill 级字段，纳检前需先有域化后的值域——**随 P2 产物契约域化一起做**）；(c) NodeArtifactModal 按 kind 注册表分发渲染 → **挪 P2**（渲染分发器是产物契约域化的另一半）。⑤真脑 fixture 同 P0 注记移 P2。

### P1.5 决策闸（线C，v2 新增，时序前移到 P2 之前）

**背景（实测事故，2026-10-30 需求分析线程查库实锤）**：AI 列了 4 个 GPU 选项问用户选哪款——纯文本问询、零问询卡（全线程无任何 HumanQuery/options 消息），问完 4 秒后自行选了第 3 选项（非自己标注的推荐款）落定出件。根因三层：①大脑没调 ask_user，文本问询不进"发卡→占协议槽→停轮"链路；②调和器 R2 只投影工具闸记录，内容性问询不在雷达内；③停轮机制只认登记缺口——AI 自己把 GPU 型号槽填了 → 无缺口 → 不停。

**执行内容**：
1. 节点契约新增决策点声明（画布抽屉"决策点"区）：`decision: {question, options_source, recommended_key, allow_other}`——选项=库内候选自动生成；配置者定语义，引擎保执行；
2. runtime 决策闸：声明了决策点的节点执行时，若该决策槽位**无用户信号**（无用户点选/输入的问询答案记录，AI 自填不算）→ 引擎发 HumanQuery choice 卡并停轮（复用 10-23 问答协议，不新建卡种）；
3. 调和器不变量族添 **R5（决策问询存在性）**：决策节点完成但既无问询也无答案 = 违约 → 拦截出件并如实报错（建议处置，待拍板；备选=强制重调一轮）；
4. 校验条款纳检：决策点声明的字段完备性（question 非空、options_source 合法）入 `flow_validation`（error 级）；
5. 左栏规则同步降维：多候选行为条款删除，由机制保证（"行为规则能降维成协议不变量就降维"——10-23 既定方向）。

**目标**：AI 永远不代答用户决策；多候选场景卡必弹、轮必停、用户拍了才继续。
**预计效果**：内容性问询从概率行为变成机制保证；闸家族（缺口闸/确认闸/问答协议）补齐第四闸，范式可复制到后续所有决策类场景。
**校验（自动化）**：①考卷场景：多候选流断言"有问询记录、无自行落定"；②负向：AI 自填决策槽 → 引擎拦截；③R5 违约注入测试。
**用户验收**：真机跑一次多候选需求（如 GPU 显存精确 64G 只有国产款），确认卡弹出、recommended 置首、Other 可输入、点选后流程继续且落定款=用户所选。
**风险与回滚**：未声明决策点的存量流=保持现状（不破坏）；声明配置错误 → 校验器保存期拦截；回滚=移除 runtime 读取分支（配置键保留）。
**待拍板三点**：~~待拍板~~ **已按建议拍板落地**（声明位置=流节点配置 / 无信号判定=答案归档查询 / 违约处置=闸上机械拦截，compose 级列 P2 加固）。
**执行注记（2026-10-31 落地+真脑 E2E 两轮）——三处方案修订，以此为准**：
- **声明形状演进**：实际落地 `decisions[] = {slot, match_category, question, min_candidates, allow_other}`——`match_category + min_candidates` 替代原设想的 `options_source/recommended_key`（kp 域的选项本就该从库内候选池自动生成、AI pick 作推荐默认项；声明只需圈定"哪个类目要拍板"与触发阈值）。本节上文的原字段形状作废。
- **闸点架构（重要修订）**：原设想"声明了决策点的**节点执行时**发卡停轮"——E2E 实测发现决策不在节点边界：配件落料走确定性 kp 插件+part_landing（大脑只经 fill kp_rows 重提交料号名），**AI 代答发生在落料函数内部**。因此闸装两点：①`phase_kp_reason` 落料降级（声明类目行无用户 pick → 剥名降级为未匹配白盒 → 行走行卡反问，选项=库内候选池）；②`select_parts` 点名锁定路径 `part_lock_verdict`（card/refuse/allow 三态；**协议状态 fail-closed**——已有开放问题=拒绝自填，堵重试代答后门，首轮 E2E 实锤后收紧；仅候选检索异常才 fail-open+degraded）。两闸点已在 ABI 分册二命名——**未来第三条落料路径接入时必须同样过闸**。
- **R5 v1 形态**：闸上拦截（写路径机械拒绝自填=自答结构性不可能）；compose 级出件拦截列 P2 加固。
- **左栏降维未做**（尾巴）：多候选行为条款仍在左栏，机制已兜底，条款删除随 P2 左栏规则修订一起。
- **已知缺口（记录在案）**：**机型选型（select_model）的决策闸未覆盖**——它有候选池接地+"无法决断时不锁定"纪律，但纪律仍是概率组件。v1 范围=配件类目决策闸；机型域列入 P2 观察项（实测出现多候选代答即提级）。
- **E2E 实录**：首轮抓"闸守错门+fail-open 漏洞"（本节修订的直接依据）；二轮绿——GPU 行停轮（pause=stuck/kp_pick resumable）、行卡 4 候选、点选智铠→7.2s 落定=点选款、finished=true。设计细节：docs/决策闸设计-P1.5.md。

### P3 工具契约升级 + 确认分级 + 写后回读（线C 核心）

**执行内容**：
1. `_TOOL_SPECS` 扩展结构化字段（命名对齐 MCP 注解，见 §6 参照 1）：`effects: "read"|"write"`、`destructive_hint: bool`、`idempotent_hint: bool`、`confirm_policy: "none"|"stage"|"stage+consent"`、`confirm_threshold`（可选，金额/数量）、`required_permissions: [...]`、`target_entity: str`；`tool_catalog()` 与 `GET /api/assistant/tools` 带出；
2. 确认分级落地：`none`=免卡（仅限 idempotent_hint=true 且无资金/外发语义的白名单工具，如暂存附件类）；`stage`=现状预览卡；`stage+consent`=现状确认卡+外发审批闸。分诊决策者=**声明策略**（可解释、可审计），不是模型判断（对照 OpenAI auto-approval 子代理思路，见 §6 参照 5）；
3. 写后回读强制化：写语义工具统一走 `execute_and_verify` 包装——执行 → 按该工具声明的探针回读真实表 → 结果事实里带回读数据（落了什么/id/行数）；回读不符 = 结果为 error 事实 + 案台不算成功。`set_quote_margin`/`submit_cost_sheet` 等存量写工具逐个迁入。

**目标**：工具 = 机器可读契约；写操作 = 声明确认策略 + 强制对账。
**预计效果**：①未来独立引擎/外部业务系统按契约插拔工具（L2 的前提）；②确认卡总量下降（低影响免卡）而高危不减——直接缓解 10-22 那批"卡迟到/四连卡"摩擦；③"写了但没写对"一族问题（confirm 绕闸/重导抹价）被回读机械封死。
**校验（自动化）**：①注册表完整性测试：每个写工具必须声明全部契约字段（缺=红）；②负向用例：mock 回读不符 → 工具结果必须为 error 且旗标不落；③真脑交付全链 E2E：基线 169.9s，允许 +10% 以内，全链产物一致。
**用户验收**：跑一次完整交付流，数确认卡张数（预期比现在少）+ 逐张核对产物；故意造一次回读不符（如改库后再触发），看大脑是否如实报错。
**风险与回滚**：免卡档误伤 → 初始白名单从严（只有幂等+无金额语义的工具）；回滚 = 全部 confirm_policy 改回 stage+consent 即现状。

## 5. 你没提到、但要想的 12 件事

1. **"独立"的定义与陷阱**：独立 ≠ 拆微服务。单机单宿主时服务化只有成本没有收益（L3 明确缓做，判据=第二个真实宿主出现）。业界反例见 §1.3：产品价值在协议与机制，不在部署形态。
2. **双运行时收敛路线**：终态是"一个内核协议、N 台运行时"，不是合并成一台（推理管道与事务内核的编排风格本就不同）。已收敛的：问答协议、事件协议、画布。未决的：`slots_backfill.py` 建了 8 个月零调用点——**要么接线要么删除**（Principles 只增不删，挂着就是误导），建议 P1 顺带决断；`workflow_ask↔ask_user` 双轨在问答协议落地后应已消除，P0 基线时核实销账。
3. **流的版本化与迁移**：流配置现在靠 rules.reasoning_flow 版本号手工推进（v159/v160 实录）。类比安卓 Room 的 schema 版本 + Migration（你在鹦鹉 App 里刚做过 6.json）：流配置也该有 schema_version + 显式迁移函数，升级不靠"在线确认"口谕。P0 时把当前版本机制文档化，P6 时给 DSL 定 v1。
4. **失败语义与补偿**：案台现算（不信任叙事、步骤指针=第一个产物未落者）本质是 saga 模式的雏形——每步幂等可重推、状态可从真实表重建。值得在 ABI 文档里正式命名并写明保证（崩溃后恢复到哪一步、什么情况需要 fresh 装填），这是引擎"强壮"的核心卖点。
5. **观测性**：`backend/logs/app.log` 已落文件。建议追踪字段命名对齐 OTel `gen_ai.*`（回合 span、工具 span、消耗 token 数），将来接任何观测平台都不用改语义。规范仍 experimental，只取命名不引依赖。
6. **成本治理**：需求分析已有"AI 增强预算"（快/均衡/最优三档）。推广为**每条流的预算档位声明**进流配置（哪些节点准用大模型、几轮封顶），审计面板展示每次开工单的 token 消耗——企业场景迟早被问"这条 AI 流一次多少钱"。
7. **注入面安全**：上传成本表解析是天然的提示注入面（文件内容流进大脑上下文）。C1 纪律（工具只摆事实）已是对的第一步，建议加显式防线：解析产物进上下文时打"数据非指令"标记 + 基线夹具里加一条注入样本（文件里藏指令，断言大脑不执行）。MCP 官方安全实践同款思路（§6 参照 1）。
8. **确认摩擦的分级**：见 P3。核心观念转变：确认卡不是越多越安全，是**分诊**——低风险自动、高风险人审（OpenAI 实测分诊后打断次数降约 200 倍）。你们的调和器已经是分诊的执行机构，缺的只是把"谁该分到哪档"从隐式惯例变成工具契约声明。
9. **多租户/命名空间预留**：`flow_key`、工具名、`state_slot` 现在是全局平铺。独立化后若多业务域接入，需要命名空间（如 `cpq/delivery_to_quotation`）。不必现在改，但 P0 的 ABI 文档里把命名规则写死（"kebab-case、域前缀预留"），避免将来撞名迁移。
10. **文档治理**：frontend-pages 文档 10-29 已删——教训是**规范的长效载体只能是校验器+模板+测试**（机器执法），文档只做导航和 why。每个 Phase 产出里"文档"都排在"测试"后面，是有意的。
11. **评测资产化**：P5 的场景夹具是资产不是脚手架——跟流一起进 git、一起评审。真脑 E2E 计时（169.9s/173.0s 这种）留档作为性能基线，回读强制化上线后对照。
12. **AI↔AI 协作通道**：办公室里同事间至今没有私聊通道（10-02 文档明记"AI↔AI DM 无内容源，待产品拍板"）。若将来要做，协议参照 A2A（§6 参照 4，150+ 组织、Linux Foundation/AAIF 托管）——但当下不做，只在 ABI 文档里给事件协议留一个 `agent_to_agent` 事件族的位置。
