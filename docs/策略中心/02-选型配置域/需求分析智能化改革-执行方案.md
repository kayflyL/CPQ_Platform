# 需求分析智能化改革 · 正式执行方案

> 版本：v3（2026-08-10） · 状态：**Phase1/2/3 全部完成**（核心改革落地，见 CHANGELOG [0.1.51-53]）
> 触发：8 卡 GPU 需求实测——方案助手（纯 LLM）分析又快又准，需求分析（13 节点工作流）又慢又错（内存 16G×1 / 电源 2000W / RAID 丢失 / 网卡 400G）。
> 原则：**该删就删、该合并就合并，不被既有架构束缚**；分阶段落地，每阶段可验证、可回退。

---

## 一、问题定性（三句话）

1. **智能碎片化**：一个完整判断（"这配置有什么问题"）被拆成 understand/gap/scene/model/kp… 每节点只见片段，LLM 整体推理在槽位边界被丢弃。
2. **规则字面化**：正则/关键词/规格过滤永远追不上自然语言（256GB 是总量、2GB缓存8口=9361-8i、R9700 是 300W 卡——规则全认不出，LLM 全认识），且**错误的自动答案比没有答案更糟**。
3. **双路径包袱**：每个功能做两遍（AI 路径 + 规则兜底），规则路径是二等公民还天天打补丁；"AI 失效用正则假装理解"是历史遗留，是系统无法完全智能化的**症状**（根因是"规则优先、LLM 只做增强"的设计哲学）。

## 二、目标架构

从「规则管线」改为「**AI 员工 + 工具 + 校验**」：

```
现在（13 节点，规则主导）                    改革后（6 个角色，LLM 提议 + 库校验）
─────────────                              ─────────────
理解 → 缺口 → 场景 → 机型 → KP → 合规       ① 需求理解+专家分析（LLM 整体读：
  → 组装 → 预算 → 审计 → 自纠 → 就绪         槽位 + 问题清单 + 缺失项）← 方案助手第一段
                                          ② 机型选择（规则+多级放宽，白盒）
                                          ③ KP 提议 + 库校验（LLM 提议 → 库精确校验）★
                                          ④ 方案组装（确定性）
                                          ⑤ 方案校对 judge（独立裁判 + 规则事实）
                                          ⑥ 反问 / 就绪
```

**核心分工（一句话）**：LLM 只提议（理解/分析/配件/反问），库与规则只执行与校验（料号/价格/兼容 100% 确定性）；**LLM 提议的东西必须过库校验，库是唯一事实源**。

## 三、改革内容（按模块）

### A. 核心改革：KP「LLM 提议 + 库校验」（改 kp_reason）
- **现状**：LLM 只确认规则匹配结果（ReAct 调 pick_kp_parts），规则按关键词/规格字面匹配 → 认不出"256GB 总量、2GB缓存8口、R9700 功耗"。
- **改后**：LLM 读「需求原文 + 理解摘要 + 配件库知识（各类别在售件/关键规格/典型功耗）」→ **像方案助手一样提议 KP**（内存 8×32G、RAID 9361-8i、双口1G+双口10G、电源按 GPU 功耗）→ 系统**逐条在配件库精确校验**（名称/型号 token + 规格匹配）→ 用库真实料号/价格出 BOM。
- **防幻觉红线**：提议件在库中精确命中才采纳；未命中 → 标记"待确认"走反问/人工，**绝不静默替代、绝不编料号**。
- **可配置**：`kp_reason` 抽屉——`proposal_mode`（llm_propose / rule_fallback）、`verify_strict`、`max_proposals`、提示词可覆盖。

### B. 理解节点升级「专家分析」（改 understand）
- **现状**：LLM 只填槽，缺"这配置有什么问题"的分析。
- **改后**：LLM 输出 = 槽位 + **问题清单 issues[]（含依据/建议）**（如"电源不足：8×R9700+2×9354 满载>4000W，建议≥4×2700W"）+ 缺失项。issues 展示给用户（方案卡/对话里），并作为 kp_reason 提议的依据。
- gap_analyze / scene_decide 的能力并入本节点（LLM 自己判断缺什么、什么场景）。

### C. 删除历史包袱（AI 失效第二套智能）
- 删除 `extract` 节点作为"AI 失效理解兜底"（requirement_parser 正则理解自然语言）
- 删除 `run_rule_understand` 的"理解需求"路径、`ai_mode: rule`（纯规则理解）
- 收敛 `requirement_parser`：仅保留**结构化表单/固定格式**解析为工具函数，不再作为自由文本理解路径
- 清理为规则路径服务的配置/测试（关键词上限、model_token_regex 规则匹配等）
- 这些删除是**必要不充分**：必须与 A/B 一起做，否则删完系统照样不智能。

### D. 诚实降级改造（AI 不可用 ≠ 跑更差的规则）
- **保留**（可靠性工程，不是包袱）：LLM 调用重试 + 防空回（分步理解机制）；编排 LLM 挂 → 拓扑序线性跑（hybrid spine 已有）；校验层（llm_audit/result_check）。
- **改造**：AI 全局不可用（断网/额度）时 → **明确告知"AI 引擎暂不可用，请走手动配置" + 目录引导手动选型**（选项 100% 来自真实目录，零幻觉）——保留 `_ask_catalog_question`，语义从"规则假装理解"改为"AI 不在，请人来选"。
- **绝不**：偷偷用正则解析自由文本输出"看似方案实为错误"的 BOM。

### E. 配套子修复（不改革也要修，直击 8 卡案例）
| 问题 | 修复 |
|---|---|
| 内存 16G×1 | memory 槽位加 `total_gb`（256GB 总量不丢）；kp 提议按总量+通道知识拆条数（8×32G） |
| 电源 2000W | PSU 推断改为**按配件库 GPU 实际 TDP** 估算（删 `high_tdp_gpus` 硬编码清单，改配置驱动） |
| RAID 缺失 | 允许 LLM 按规格提议型号（2GB缓存+8口 → 9361-8i）→ 库校验 |
| 网卡 400G | "2x 1GE/2x10GE" 解释放宽 → 匹配双口卡（i350/X710），LLM 提议 + 库校验 |

## 四、流程图变化（节点增删合并）

**保留（可靠底座）**：目录/配件库（SSOT）、`compose`/`build_plan`、`select_models` 多级放宽、`merge_into_ext`、`llm_audit`（judge）、`result_check`、`llm_ask`（反问）。

**合并**：`gap_analyze`+`scene_decide` → 并入 `understand`（专家分析）；`spec_compliance` → 并入 KP 校验 + compose 校验。

**删除**：`extract`（AI 失效理解路径）、`ai_mode: rule`。

**降级为可选能力（画布仍可拖，不报错）**：`gap_analyze`/`scene_decide`/`spec_compliance`/`audit_fix` 等旧节点保留在 palette，但**默认执行链不再经过**。

**默认执行链（改革后）**：
```
understand(专家分析) → model_reason(多级放宽) → kp_reason(提议+校验) → compose → llm_audit(judge) → review
```
（llm_ask 在需要反问时插入；总共 ~3 次 LLM 调用，目标端到端 40-60s）

## 五、分阶段执行（每阶段有验收与回退）

### Phase 1 · KP 改革 + 子修复 + 删 extract 理解路径（核心正确性）
- 改 `kp_reason`：LLM 提议 + 库校验（A）
- 子修复 E：memory total_gb / PSU 按 GPU TDP / RAID 规格提议 / NIC 双口
- 删 `extract` 理解路径、`ai_mode: rule`、`run_rule_understand`（C，理解路径部分）
- **验收**：8 卡需求 KP 结果接近技术员方案（8×32G / 9361-8i / 双口1G+双口10G / 480G×2+SSD / 8×R9700 / 2700W×4 / 9354×2）；后端 pytest 全绿；前端 vue-tsc 绿
- **回退**：`kp_reason` 保留 `proposal_mode=rule_fallback` 开关，一键退回旧匹配

### Phase 2 · 理解升级专家分析 + 默认链收敛 ✅ 已完成（见 CHANGELOG [0.1.52]）
- `understand` 输出 issues[]（B）；gap/scene 并入；spec_compliance 并入校验
- 默认 active flow 收敛为 6 节点（旧节点 palette 保留）
- **验收**：模糊需求先给"问题分析"再反问，交互接近方案助手；详细需求直接出方案含 issues
- **回退**：画布节点回退到旧图即可恢复旧链（图 = 能力注册表，天然可回退）

### Phase 3 · 诚实降级 + 清理 ✅ 已完成（见 CHANGELOG [0.1.53]）
- D：AI 不可用 → 告知 + 目录手动选型
- 清理规则路径残留配置/测试/文档
- **验收**：模拟 AI 不可用（关全局开关）→ 走手动选型，不再出"假智能"BOM
- **回退**：降级行为由配置控制，可调

## 六、验收标准（8 卡需求 · 对标技术员方案）

| 项         | 技术员方案                            | 需求分析现状    | Phase 1 目标         |
| --------- | -------------------------------- | --------- | ------------------ |
| 内存        | 32G×8                            | 16G×1 ❌   | 32G×8（256GB 总量）    |
| RAID      | LSI 9361-8i                      | 缺失 ❌      | LSI 9361-8i        |
| 网卡        | 双口1G + 双口10G(光模块)                | 400G模块 ❌  | 双口1G + 双口10G(光模块)  |
| 电源        | 2700W×4                          | 2000W×4 ❌ | 2700W×4（按 GPU TDP） |
| CPU/GPU/盘 | 9354×2 / 8×R9700 / 480G×2+960G×2 | 对 ✅       | 保持                 |
| 端到端耗时     | —                                | 70-95s    | 40-60s             |

**三场景回归**：详细需求（直出方案）/ 模糊需求（专家分析+反问）/ 点名库外机型（多级放宽+白盒说明）。**AI 不可用场景**：告知 + 手动选型。

## 七、风险与对策
- **模型偶发空回/慢**：重试 + 防空回（保留）；轻 prompt 分步（已做）
- **LLM 提议幻觉**：库精确校验 + 未命中标记待确认（红线）
- **库数据不全**（如无 1TB SSD，只有 960G）：替代件白盒标注"容量替代"（已有机制）
- **外部 API 依赖**：诚实降级（告知+手动），不做"假智能"

## 八、明确不做（防止范围蔓延）
- 不引入 Hermes / 实在 Agent 整套（跨系统 UI 操作 RPA 与本项目无关，只搬认知层与闭环）
- 不换底层模型（cloudprime + deepseek-v4-flash 是硬约束，judge 用独立角色 + 规则事实防塌缩）
- 经验沉淀（bom_cases 自动入库）**不做**（用户已否决：怕乱加案例）
- 不做"每步都问 LLM 该走哪步"的纯自由 agent（慢且不可控，已用 hybrid spine 取代）
