# 蓝图：编排器读画布拓扑（A 方案 · 待确认）

> 目标：让「需求分析画布」成为 Graph Orchestrator 的唯一拓扑真源。
> 用户在画布上增删节点 / 改连线 / 改 label，编排 agent 的能力池、就绪约束、执行顺序、白盒展示全部跟着变。
> 现状根因：`reasoning_orchestrator.CAPABILITIES` 是代码硬编码的 11 步链，执行只读 `flow.node_configs`，
> **不读 `flow.graph` 的 nodes/edges** —— 所以画布改图对执行无感。

---

## 1. 映射规则（图 → 编排器）

### 1.1 节点分类（执行时按 type 识别）

| 类别 | 判定 | 处理 |
|---|---|---|
| **能力节点** | type ∈ `_dispatch` 支持集（见 §2 的 11 个） | 加入能力池，可被编排 agent call；label 用画布节点 label |
| **反问节点** | type = `llm_ask` | 不是 step：映射为编排器的 `ask` 动作（走 `run_llm_ask`），不入能力池、不参与 deps |
| **兜底节点** | type = `extract` | 不是 step：由 `understand → extract` 边触发「AI 失效规则兜底」（沿用现有 `understand_fallback` 机制） |
| **条件节点** | type = `condition` | 本编排模型无分支语义（v12 已删 cond_*）；执行时跳过，但作为**透明桥**参与依赖推导（入边源 → 出边目标 直连） |
| **未知类型** | 其它 | 跳过 + 日志警告，不阻塞（用户新画的节点需要先有后端 handler 才会执行） |

### 1.2 依赖推导

- 取画布 edges，过滤掉源/目标是 `llm_ask / extract / condition` 的边（condition 先做透明桥直连）
- 剩余正向边构成能力 DAG：`deps(node) = 该节点的直接前驱能力节点`
- **边的 `source_handle` / `condition` 不参与推导**：本模型是「能力池全部执行、LLM 选顺序」，不是分支语义；true/false 分叉到两个能力节点时，两个都算依赖、都可能被调用
- 就绪 = 前置能力全部完成（沿用现有 `_ready_capabilities` 逻辑，只是 deps 来源从硬编码换成图派生）

### 1.3 起止与兜底

- **起始**：能力 DAG 中入度为 0 的节点（当前 = understand）；**终点**：出度为 0 的节点（当前 = review）
- **final 判定**：全部可达能力节点完成（不再硬编码「review 完成」；review 仍是默认终点）
- **兜底**：图缺失 / 能力 DAG 成环 / 无能力节点 / 校验失败 → 退回内置 `CAPABILITIES`（现状）+ warning 日志；线性兜底顺序 = 能力 DAG 拓扑序

### 1.4 确定性红线（去硬编码）

- `deterministic` 从代码硬编码改为**节点配置项**（画布抽屉可开关），默认值 = 现在的硬编码集合：`spec_compliance / compose / budget_check / audit_fix / review`
- 旧 flow 不用迁移（默认值一致，行为不变）；用户可在抽屉改

### 1.5 明确不做（本次范围外）

- **自纠回边**（`retry_caps`：spec_compliance 补卡 / budget_check 降配 / audit_fix 自纠）保持运行时信号，**不画成画布边**——避免把 DAG 推导复杂化；以后要可视化再加
- 不实现「画布上新增一个后端不认识的新能力类型」（那是开发新能力，不是配置）
- 不引入真分支/并行执行语义

## 2. 节点清单（13 个，与画布一致 · 数据来自 active flow 125）

| 节点 | 职能 | 确定性红线 | 抽屉可配置项（现状） |
|---|---|---|---|
| understand | 需求理解：LLM 领域知识 + 填表（catalog 白名单锚定），AI 失效→extract 兜底 | 否 | ai_mode / case_match / case_source / case_top_k / intent_words / keyword_limit / lexicons / model_token_regex / qty_multipliers / qty_units / spec_aliases / system_prompt |
| gap_analyze | 缺口分析：判定理解是否够；够→scene_decide，不够→llm_ask | 否 | llm_explain |
| llm_ask | 智能反问（ask 动作，非 step）：策略/分档/目录选项/文案 | 否 | ask_user / max_rounds / scale_tiers / strategy / use_catalog_options / workload_categories |
| scene_decide | 场景判定：AI/存储/通用 + 系列/形态 | 否 | ai_mode / decide_threshold / fallback_scene |
| model_reason | 机型推理：ReAct + select_models 锁机型 | 否 | ai_mode / enabled_tools / fallback_order / max_iterations / max_plans / no_signal_strategy |
| kp_reason | 配件推理：ReAct + pick_kp_parts 定配件 | 否 | ai_mode / category_aliases / cpu_mem_type_rules / drive_spec_substitute / enabled_tools / fallback_strategy / max_iterations / representative_pick / spec_rules / type_packages |
| spec_compliance | 规格合规校验：AI 缺卡补 / 存储缺盘 / CPU 降级标 issue / 内存代际 | **是** | enabled / mode / gpu_required_for_ai / cpu_mem_generation / max_fix_rounds / strict_model_match |
| compose | 方案组装：整机方案（KP 行） | **是** | kp_per_baseline |
| budget_check | 预算校验：超预算自动降配 | **是** | auto_downgrade / downgrade_axis / underspend_threshold |
| llm_audit | 方案校对：LLM 事后审计 | 否 | enable_llm / reference_limit |
| audit_fix | 审计自纠：检出→补 GPU/抬内存→确定性重跑 | **是** | enabled / max_retry / only_critical / retry_scope |
| review | 方案就绪：BOM 输出/最终总结 | **是** | bom_output / recommendation |
| extract | 规则理解兜底（AI 失效）：requirement_parser 正则解析单点出口 | 否 | keyword_limit / model_token_regex / note |

> 注：active flow 125 有 15 条 node_configs（含遗留 `cond_gap`、`ask_user` 配置，图里无对应节点）——按「该删的删掉」原则，这次可顺带清理。

## 3. 前端改动（小）

1. 画布抽屉：每个能力节点加 `deterministic` 开关（默认勾选 = 现状红线集合）
2. 节点 label 已有（画布即真源），编排器广播 step 时用画布 label
3. 可选：未知类型节点在画布上标「编排器不支持，执行时跳过」提示

---

## 4. 迁移 / 兼容

- **active flow 125 图正好是 v12 链**：从图派生的能力 + deps 与现在 `CAPABILITIES` **逐节点一致**（已手工核对：understand→gap_analyze→scene_decide→model_reason→kp_reason→spec_compliance→compose→budget_check→llm_audit→audit_fix→review）→ **零行为变化**
- 老 v9 双路图若被激活：含大量 condition/llm_agent/extract 节点 → 派生后能力池变小/校验失败 → 自动兜底内置链 + 警告；不迁移老图
- 新增 `deterministic` 配置项默认值与现状一致，存量 flow 无需数据迁移
