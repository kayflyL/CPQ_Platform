做完**视觉类改动**（CSS / 布局 / 渲染 / 字号行距 / 颜色 / 对齐）后，**简述改了什么就停**，让用户在自己的运行实例里自己看一眼确认。**不要**主动 `preview_start` 起 frontend、导航、驱动下拉/按钮去加载预览数据来"自验证"。

**Why:** 用户自己有运行中的 app，视觉东西他扫一眼就能判断对错；而我走浏览器验证要起服务、找路由、驱动 UI 加载预览数据，慢且开销大，纯属多余。原话：「以后这种视觉上的，可以优先让我确认，我如果解决不了你再接入」。这次改规格书条款对齐时我花了一堆 preview_eval 驱动商机选择加载预览，用户其实自己已经看过了。

**How to apply:** 视觉改动 → 改完说明就停，等用户回话。只有以下两种情况才动用浏览器自验证：
1. 用户反馈「我看不出来 / 改不动 / 还是没生效」，明确求助时；
2. **非视觉**的逻辑/数据 bug，尤其反复修不好时——按 [[feedback-verify-yourself-dont-bounce-user]] 自验证。

**渲染产物（Remotion 渲染的 PNG 帧/MP4 视频、其他截图/图片产物）同样属视觉**：直接给文件路径让用户看，别用 python PIL 像素采样、preview server 起静态站截图等绕路"代替眼睛"。原话「视觉上我来帮你看就可以」。本环境 Read 图片本就返回 Unsupported，绕路成本高且人眼扫一下比像素采样准得多。

两条不冲突，触发域不同：视觉 = 先让用户看；顽固 bug = 自己复现别踢给用户。相关：[[scoped-global-pitfall]]（视觉必查 getBoundingClientRect 而非截图——但前提是要查才查）。

**延伸（2026-09-16 门户策划）：布局级设计用户要自己来。** 给用户出两套门户布局 mockup 让选，原话「算了，都不太行，我等会自己设计吧」。布局/信息架构的方向性设计，我的角色是供给**数据事实清单**（哪些后端数据现成可用、改造成本），不是替他出方案选型；动手前等他给出自己的设计。

**2026-09-19 强化（美化为「高大上」翻车）：视觉升级类任务必须先出设计方案审核，禁止直接动手。** 用户说「门户工作台搞得高大上点」，我调研后直接实现了整套 Magic UI 动效（极光背景/流光边框/跟随光斑…），用户：「好丑啊你为什么不先出设计方案让我审核，而是直接动手了，还做得这么丑？撤回」。**Why:** 审美判断权在用户，我的默认品味不可信；跳过审核=白干+撤回成本+伤信任。**How to apply:** 「弄酷炫点/高大上点/优化下视觉」类需求 → 先给设计方案（2-3 个方向 + 每个效果一句话描述 + 参考出处），等用户拍板（或改）后才写代码；调研（找案例/扒实现原理）可以做，但产物是方案不是代码。小修小补（对齐/颜色微调/修渲染 bug）才适用旧规则「改完让用户看」。

**2026-09-19 补记（星河首页复刻）：「记住先做原型图」+ 放宽视野。** 大型视觉改版的固定流程 = ①调研原版（可把原站镜像到本地实测跑通，逐阶段截图拿完整分镜）→ ②出可运行原型/原型图给用户审 → ③批准后才动真代码。用户二次纠偏「不要自己乱编」：凭反编译代码脑补细节（DoF/流光/调色）而没看过原站整体构图，导致方向性返工——**先看整体再抠细节**。镜像方法已验证可行：curl 走本地代理(10809) 拉 archive.org 资源到 `_by_mirror/` 本地起服务跑原站（注意补齐 exr/exr 类纹理和改写 CSS 里的 archive 前缀 URL）。
