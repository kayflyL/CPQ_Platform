## 为什么选择workflow
### 1.1 最初的需求：让 AI 学会做配置方案
功能的起点很简单：我想用 AI 自动生成服务器配置方案，作为把AI的能力引入CPQ报价系统的第一站。

面向装备、汽车、服务器这类选配、BOM生成场景，行业内已经有成熟的路线。在AI大模型兴起之前，一般是通过产品配置器选配，提前把所有配件的兼容、互斥规则录入系统，形成配置约束引擎。前端给用户一个向导式选配页面，用户一步步选参数，配置引擎则实时根据底层校验规则自动拦住不能选的组合，返回合规配件，比如选了兆芯平台的服务器机头后，后面不兼容的配件选项直接置灰、不可勾选。

AI时代，这类产品正被重构，过去的操作流程就像：
[用户需求] -> [人理解需求，信息不足或不确定时向用户发问] -> [根据需求操作配置器选配，过程中自主思考下一步选什么] -> [选型配置器做合规校验] -> [完成方案配置，做配置表] -> [输出给用户]

而 AI 特点是在自然语言理解上优势突出，在需求理解阶段它可以承接用户口语化、碎片化的需求描述，拆解出平台、性能、预算等关键约束，补齐缺失参数并主动确认模糊信息。但 AI 本身并不擅长保证硬件选配的合规性，所以选配过程不能简单的用提示词+skill+配置规则的组合完成，因为AI是概率生成模型，不是确定性执行引擎，随着会话越长、规则越多，AI对用户输入内容的遵循概率会越来越低。而skill本质上是增强版的提示词，他可以引导AI做事，但不是强制约束，躲不过AI上下文长了生成的内容就漂移的问题。而服务器配置涉及需求理解、规则判断、数据查询、配置组装和结果校验等思考和执行过程，尤其涉及真实物料，价格和配置规则，需要可控、无幻觉。

所以需要将服务器方案配置过程用Workflow编排引擎固定下来，将每一步要完成的目标，需要遵循的规则和输出物都做好配置。大模型把自然语言需求转化为结构化选型参数，再交由底层配置约束引擎物料匹配、互斥兼容判断（例如选定兆芯平台机头后，不兼容的主板、电源、扩展卡等配件自动置灰屏蔽），配置引擎返回合规候选集之后，大模型再基于成本、交付周期、客户偏好做择优组合、输出方案配置，所以AI时代，新的操作流程变为：
[输入用户需求] -> [AI理解需求，信息不足或不确定时向用户发问] -> [AI一手拿着用户需求，一手操作机型选型] -> [配件选配] -> [BOM 组装] -> [输出]

在这个模式下，大模型承接开放、灵活的自然语言交互，发挥它擅长理解五花八门客户需求的优势；Workflow 守住流程秩序，防止对话过程跑偏、状态丢失；产品配置器守住硬件兼容这条底线，杜绝幻觉带来的物料错配，输出符合标准的配置方案。

==================

换下一代模型只会减轻、不会消失。所以业界的解法从来不是「把提示词写得更好」，而是在架构层加三样东西：**接地（数据只能来自真实库）、护栏（确定性校验兜底）、人在环（关键拍板让人确认）**。这三样，正是我们后文整个工作流设计的出发点。

Anthropic 自己在《Building effective AI agents》里就把两条路线分得很清：**workflow 是用预定义代码路径编排 LLM，换来可预测性；agent 才是模型自己指挥自己的过程**，并明确建议「能用简单可组合的模式就别上自由 agent」。参考：[Building effective AI agents](https://www.anthropic.com/research/building-effective-agents)。

2026 年我们核查生产级案例时也得到同样结论（微软 Conductor、Backbase、Kong 等团队的公开实践）：**确定性编排包裹 LLM，确定性引擎是唯一事实源，AI 只做推理和推荐**；让 LLM 接管整条配置流水线是被点名的反模式——上下文陷阱、不可检视、贵、幻觉规则。

skill 形态解决的是「让模型知道更多」，我们需要的却是「让业务产出更可靠」——前者我们用说明书就能做到，后者必须靠工作流。**

所以我们选工作流，不是保守，是和业界结论对齐：**把确定性给编排层，把智能给节点内的 AI**。

## 设计思路：AI唯一大脑 + 确定性工作流程
传统workflow


以需求分析工作流为例，我们设计了五步工作流：
[需求分析] -> [机型选型] -> [配件选配] -> [BOM 组装] 




我们的系统现在设计是AI角色唯一大脑，workflow只是告诉AI角色，你应该走哪些流程做事情，每一步输出什么东西给下游。

而且整个需求分析skill对应的是商机详情页的前两步，agent fill对应线索登记，机型选配和配件选配对应方案配置，他们的目标输出物就是这两个商机详情页步骤对应的表格。

也就是说AI相当于在模拟人干活，人拿到用户线索，先分析需求，登记，然后传递给下游方案配置节点，方案配置技术员拿着需求表去配服务器。

由于对应的是真实业务节点的表，所以天然比如线索登记表填完，到下游就不会被回填了。

调用skill后，AI角色可以拿到skill studio 具体某个skill编辑器里的左侧栏的任务规则，这是整个skill要做的事情。中部是workflow，由一系列节点组成，AI角色接下来需要按节点编排依次执行任务。当开始任务流程时，AI角色根据skill里规划的步骤一步一步完成工作，中间有不清晰的会提问，提问应该是AI角色根据上下文需要，以及节点目标组织内容提问，而不能硬编码话术写死在各个节点里。会话窗口会显示流程步骤，中部栏会显示实时进度，比如当前运行在哪个节点了，在该节点的实时输出物，完成后可在中部栏节点查看输出物详情。

每个节点都有节点抽屉，用来配置AI角色在该节点需要完成的目标输出物，以及可调用的工具、数据、规则等资源，节点抽屉有两层：

1 目标层：节点的目标输出物，可以是表格、文档、PPT甚至是图片。这一层同时也承担输出给下游的数据，下游拿到上游节点的输出物后开始工作。目标层典型的输出物是表格，表格输出物的设计是左侧是字段，右侧是表格预览，字段可勾选是否必填反问，如果勾选，那AI角色必须填这个字段，分析不出来的时候一定要反问用户。

2 资源与权限层：包括数据、规则、工具。

2.1 数据：告诉AI角色，数据从哪里来，不要自己编，在本系统中，数据来源于系统内部，代表性的有服务器目录、配件库等，理论上所有页面、所有数据都可以拿到。

2.2 工具：比如有哪些机箱可以选，去机箱目录里拿数据，有哪些配件可以选，去配件库拿。去拿这些数据，肯定不能直接把大量数据灌给AI角色，因此设计了工具来解决。AI角色可以调用哪些工具，因为每个AI角色自身是绑定了工具的，但skill是公用的，也就是说可以配给任何一个AI角色，但这个AI角色不一定有这个skill层里涉及的每一个工具，所以这时候会在任务进行过程中，只要绑定了这个skill的角色，在任务几个步骤推进过程中，就自动可以使用那个工具，即使AI角色本身没绑定这个工具。

2.3 规则：系统主要功能是服务器配置，规则层是告诉AI角色，服务器怎么配，比如根据CPU决定机箱平台，当用户选择兆芯系列芯片时，机箱就得选Polaris的，当用户选择AMD系列芯片时，机箱就得选Orion系列的，等等，这一点需要慢慢补充，当然这个前提是搭好底座，规则底座入口就在策略中心-需求分析里。

系统处于建设阶段的时候，数据、工具、规则，都是不完整的，因此我们需要先设计好主干“插座”，然后再做插头，插头可以后补，重要的是系统先跑通。
