## 0. 一句话目标

配件选配（kp_reason）一个回合内：机制先把「平台作用域内的类目库存摘要」端上大脑的桌（just-in-time，几百 token），大脑按行写意图并调用约束检索工具拿 ≤4 适配池，逐行决策推荐；词法兜底卡退役；AI 没跑完的行诚实标注。**判断全在 AI（唯一大脑），机制只做物理过滤与确定性直译。**

## 1. 不做的事（防执行走样）

- ❌ 不引入向量库/嵌入检索——当前规模（类目内几十~几百 SKU、平台作用域后再缩 10 倍）SQL 预过滤 + 现有 part_lexicon 词法引擎完全够，加基础设施违反「现成实现优先」。
- ❌ 不做两段全局 LLM 编排（写意图一遍、决策一遍）——单回合内自然完成（看摘要→按行检索→决策），两遍是过度设计。
- ❌ 不改登记（agent_fill）、机型（model_reason）节点；不改 pick/recommend 落库协议（ask_option_signal/part_landing 现状保留）。
- ❌ 不在代码里写阵营词表、不写「必须先问后推」类硬规则——纪律住使用说明与工具契约，机制只摆事实。
- ❌ 不动 front-end AskCard（上一轮的下拉/数量/顺序已就位）。

## 2. 逐文件改动清单

### 2.1 `backend/app/services/data_tools.py` —— 新增两个机制函数

**(a) `category_digest(category, series, price_ok) -> dict`**（新，确定性，SQL GROUP BY）

```python
def category_digest(category, *, series: str = "", price_ok: bool = True) -> dict:
    """类目库存摘要（schema-linking 的配件版）：平台作用域内该类目「有什么」。
    大脑写选配意图前必看——约束必须引用这里的事实，不许凭空写规格。
    形状：{ok, category, total, platforms: {"Polaris": 5, ...},
           spec_ranges: {"Cores": [4, 96], "Capacity(GB)": [16, 256]},
           brands: [...], price_band: [min, max] | null,
           skus: [ ≤6 条时给全量简表(part_id/name/price/关键spec)；>6 条给空 ] }
    """
```

实现要点：
- 用 `KPRepository` + `_SeriesScopedRepo`（现成）取该类目全行（作用域后通常几十条，纯内存聚合即可，无需新 SQL）；
- `spec_ranges`：对数值型 spec key（Cores/Capacity/Capacity GB 等）取 min/max；非数值不给范围只给 distinct 值（≤10 个）；
- `skus`：总数 ≤6 时直接给全量简表（大脑零检索直接决策）；>6 给空（逼大脑走 find_parts）；
- 这就是「上万物料」问题的答案：**摘要永远按 类目×平台 切片，切片后是个位数~几十条**；全库概览不存在于任何路径。

**(b) `find_parts(category, *, must: dict, keywords: str = "", series: str = "", limit: int = 4, price_ok: bool = True) -> dict`**（新，确定性）

- `must` = 意图硬约束字典，key 必须是该类目真实 spec key（来自 digest 的 spec_ranges/distinct），value 支持 `=/>=/<=/in`（复用 `part_query` 的 `_spec_match_all`）；外加 `platform`（映射到 applicable series 过滤）、`keywords`（行描述里的词法 token，走 part_lexicon）。
- 返回 `{ok, rows: [≤4，每项 {part_id, name, price, specs, matched: {...命中了哪几条约束}}], total_unfiltered}`——`matched` 字段让大脑（和客户）看见推荐依据。
- 空池返回 `{ok: True, rows: [], hint: "无满足全部约束的料，放宽的候选方向：…"}`——hint 由机制给出「去掉哪条约束后有 N 条」（确定性提示，非 AI 话术）。

## 5. 大库存怎么拿料（技术依据，写进方案防执行时跑偏）

海量物料（ERP 万级 SKU）的正确姿势 = **切片 + 摘要 + 预过滤 + top-k**，每层都把候选数砍一个数量级：

1. **平台/兼容性作用域**（applicable 标注）：10,000 → 锁定机型平台内 ~数百；
2. **类目切片**（只看待配类目）：数百 → 每类目几十；
3. **类目摘要**（GROUP BY 聚合，毫秒级，~100 token）：大脑知道「有什么档位可写」，不读明细；≤6 条直接给明细；
4. **意图约束预过滤**（spec_filters + 词法 token）：几十 → ≤4；
5. **LLM 终审**只在 ≤4 的池子上做（判断选哪个+理由）。

全流程大脑见到的物料 token ≈ 待配类目数 × ~150，**与库总量无关**——这就是对「AI 总不能读上万条」的回答：永远不读总量，读的是切片后的摘要与 top-k。速度上 digest 与 find_parts 都是单表索引查询（毫秒级），LLM 调用从现在的多轮探索收敛到每行 ≤1 次（+最多 1 次改写）。

## 6. 模糊需求 vs 详细需求的拿料路径

- **详细（客户点名型号/规格）**：现有路径不动——lexical 精确召回（part_query keywords/lookup_parts_by_name），命中即直锁（explicit 锁定逻辑已有）；命中料与锁定平台冲突 → 冲突标注 + 适配件池 + 问客户（不静改不拦截）。
- **模糊（只有用途/场景）**：场景基线规则给数量与要点 → 意图 = 平台 + 类目 + 摘要里的档位范围 → 小类目看摘要直接决策，大类目 find_parts → 推荐理由引用基线规则（如「按 AI 训练基线：内存 2×显存」）。池空 → 1 次改写 → 仍空 → 方向性问句（容量档/性能档二选一式选项，不是开放题）。
