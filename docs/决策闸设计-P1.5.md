# P1.5 决策闸 · 设计稿（v1 定案）

> 状态：设计定案（三设计点已按建议拍板），随实现同步修订。
> 定稿：2026-10-31 ｜ 上游：白话版 §6 第 2 步、工程版 P1.5

## 0. 一句话

**节点契约声明决策点 → 引擎在锁定/写路径机械拦截"无用户信号的自填" → 自动发 choice 卡并停轮 → 用户拍板后放行。** AI 只执行，不代答。

## 1. 已拍板的三个设计点

| 设计点 | 定案 |
|---|---|
| 声明位置 | 流节点配置（画布抽屉"决策点"区）：`decisions: [{slot, match_category, question, min_candidates, allow_other}]`——配置者定语义，引擎保执行 |
| 无信号判定 | `user_signal_for(thread_id, slot)`：问答协议桶里存在 meta.slot 命中且**已被用户回答**的问询记录（answer_query 只由 /answers 端点调=永远来自用户）；AI 自填不产生信号 |
| 代答违约处置 | v1：写入路径机械拒绝自填（锁定必须过闸 → 自答结构性不可能）；出件侧 compose 级拦截列为 P2 加固 |

## 2. 事故复盘对照（本设计逐条封堵）

| 事故环节 | 本设计的堵点 |
|---|---|
| AI 列 4 个 GPU 选项没弹卡 | 闸机械发 choice 卡（open_query + announce_query），不依赖大脑调 ask_user |
| 问完 4 秒自选落定 | 锁定路径机械拒绝无信号的自填（select_parts 闸点），自选写不进 picks |
| 选了非推荐款（沐曦被标推荐却落定 150S） | 推荐标记由闸的 options 承载（recommended 置首），落定款=用户点选款 |
| 调和器雷达外 | R5 v1 形态=闸上拦截；compose 级检查列 P2 加固 |

## 3. 声明契约（流节点配置）

```json
"decisions": [
  {"slot": "gpu",
   "match_category": "GPU",
   "question": "GPU 在库有多款满足规格的候选，选哪款？",
   "min_candidates": 2,
   "allow_other": true}
]
```

- `slot`：决策槽位标识（用户信号按它归档/查询）
- `match_category`：配件类目（与 kp 行 category 精确匹配，大小写不敏感）
- `min_candidates`：候选 ≥ 该值才触发闸；默认 2（唯一候选=没有决策，直接落）
- `allow_other`：卡上允许自由输入（问答协议自带 Other 机制）
- 多节点声明汇总生效（决策是流级语义，声明在哪个写节点就近生效）

## 4. 执行序列（以 GPU 事故为例）

1. 大脑调 `select_parts` 想锁定"天数智芯150S 64G"（GPU 行，customer_specified=True）
2. 闸命中：类目 GPU 有声明 → `hybrid_search("GPU", text=行规格)` 得 3 候选 ≥ 2 → `user_signal_for` 为空
3. **拒绝锁定**：该行走 KP_RECOMMEND（大脑 pick 记为推荐默认项——沿用 2026-09-09"不许静默锁 AI 拍的料"语义）
4. 闸 `open_query(kind="choice", meta={slot}, options=3 候选+recommended 置首)`——协议单开槽不变量自动防重
5. async handler 检测 `decision_required` → `announce_query`（落消息流 kind="query" + 广播）→ 前端 HumanQueryCard 弹卡
6. 工具结果事实带 decision_required → 大脑如实转述"已发卡等拍板"、停轮（该行未锁定，方案组不齐，既有反问/暂停机制接手）
7. 用户点选 → /answers → `answer_query`（答案带 meta 归档）→ 大脑得【问题已回答】事实
8. 大脑复调 select_parts 传用户所选料号 → 闸查 `user_signal_for` 命中 → 放行锁定 → 流程继续

## 5. 机制边界（如实声明）

- **候选检索失败 → fail-open + 标注**：hybrid_search 异常时闸放行锁定，但在结果事实里带 `decision_gate_degraded: true`（可观测）——闸失效一次可见，不能把流程卡死。
- **v1 闸点只在 select_parts**（配件锁定）：fill_requirement 的 kp_rows 只登记需求行不落料，不在闸范围；机型选型（select_model）已有"无法决断时不锁定"纪律+候选池接地，v1 不动，P2 视实测纳入。
- **R5 出件侧拦截**列 P2 加固（compose 级检查"决策槽已填但无用户信号"）。
- 决策闸发的卡是**内容性问询**（choice），不走写确认 consent——锁定这个写动作本身的确认语义仍由既有工具闸承担，两闸不混。

## 7. 验收（对应白话版第 2 步）

- 考卷场景：多候选流停轮发卡（有问询记录、无自行落定）
- 负向：绕闸自填被机械拒绝
- 真机：GPU 类事故复现场景——卡弹出、recommended 置首、Other 可输、点选后流程继续且落定款=用户所选

## 8. 首轮真脑 E2E 发现（2026-10-31，实现修正的依据）

用 e2e_skill.py 直驱跑 GPU 多候选场景（203.7s 单轮），结果：**闸没拦住，AI 仍自答落定 150S**。查因：

1. **闸守错了门**：闸装在 `select_parts`（大脑点名锁定工具），但本次锁定实际走 `fill_requirement` 的 kp_rows 重提——大脑把具体料号名写进行描述后由 kp 落料路径解析锁定（`skill_node_plugins` kp 插件 → part_landing/part_selector 确定性解析，规则注释在 skill_phases.py:52-54）。
2. **fail-open 漏洞**：首次发卡后大脑重试，`open_query` 撞"单开槽"不变量抛 ContractError → 走 except fail-open 放行了自填。已修：协议状态 fail-closed——已有开放问题 = refuse（本 slot=decision_pending / 他问=other_question_open），只有**候选检索异常**才 fail-open+degraded。
3. **顺带实证**：需求分析六节点产物全部可点开（第 3 步域化前的基线）；agent_fill 白名单里本来就有 ask_user——大脑没调用，坐实"概率组件"判断。

**待办（下一动作）**：闸补装到确定性 kp 落料路径（skill_node_plugins kp 插件的落料判定，规则即 skill_phases.py:52-54 三条——命中声明类目时"直接锁定"前必须过闸），再复跑本场景至绿。该文件受宪法 C2 保护区（编排壳不认识节点名）——闸的声明仍从流配置读取（数据），不写死类目词表，符合宪法。

## 9. 机制勘察结论（2026-10-31 深查：kp 侧集成的最终形态）

深查发现 **行卡机制引擎里已经全套存在**（`skill_plan_runtime.ask_option_signal`——"唯一出口：卡怎么发射，信号就怎么解释"）：

- **行卡**（row_key 非空）：选项带 `pick`=落地料号（点击经 `kp_manual_pick` **直接落地真实料号**）、`absent`=类目不配（GPU 逃生）、`waived`=行豁免（保留+标注）、否则并入行描述；
- **pick_all**：「全部按推荐落定」批量晋升信号（`kp_accept_recommendations`）;
- **字段确认卡**：slot+value 点选即登记并记「客户已确认」。

因此 **kp 侧集成的最终形态 = 不新写发卡代码，只改触发条件**：kp 阶段逐行"落料 vs 发行卡"的判定里，命中决策点声明的类目在（多候选 ∧ 无用户信号）时**改发行卡**（选项=库内候选 pick、recommended=AI pick、absent/waived 逃生项照带）——用户点选经 `kp_manual_pick` 直接落地，闭环零新增协议。定位残留：kp 阶段逐行判定的执行函数（候选池在 `part_recall.resolve_kp_pools`/part_selector，行卡发射在 runtime）——下一动作的精确目标。
