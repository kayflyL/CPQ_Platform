# AI 办公室 · 业务系统 · 工作流：架构关系图

> 本文是《[AI办公室引擎化方案（白话版）](AI办公室引擎化方案.md)》§3 的图解篇，把三者的关系、传递的数据、需要的接口一次画全。
> 定稿：2026-10-30

---

## 0. 先纠正一个直觉：不是三个并列的系统

"业务系统、AI 办公室、工作流"听起来像三个东西并列，其实**工作流不是第三个系统**——它是**住在引擎里的程序**：只有定义数据（图谱/节点/规则）和一份声明，没有自己的进程、没有自己的数据库、没有自己的状态。它的"状态"就是业务真表 + 引擎里的步骤指针。

所以三者的真实角色是：

| 角色 | 类比 | 它是什么 |
|---|---|---|
| AI 办公室（引擎） | 地面 + 交通规则 + 车管所 | 机制层：跑工作流、管工具调用、弹确认卡、记账 |
| 工作流 | 车路上跑的某辆车 | 声明+数据：一条被引擎执行的流程（需求分析/交付/趋势…） |
| 业务系统（CPQ、人事培训…） | 加油站 + 唯一的真实地图 | 能力与事实源：提供工具（服务函数）、页面（产物窗口）、数据（真表） |

## 1. 角色总图

```
            人（唯一特权方：两条路都能走）
   ┌─────────────┴─────────────┐
   │                           │
 甲路：直接用业务页面             乙路：在 AI 办公室里
 （查价、填线索、四步报价）        聊天 / 看画布 / 点确认卡 / 开工单
   │                           │
   │                           ▼
   │        ┌─────────────────────────────────────────┐
   │        │            AI 办公室（引擎）               │
   │        │  ──────────────────────────────────     │
   │        │  门面：办公室视图 · 同事聊天 · 画布 · 任务板  │
   │        │  运行时：事务内核 · 推理引擎                │
   │        │  机制：工具执行器(权限→确认→执行→回读→审计)   │
   │        │        探针/案台 · 事件广播 · 发布校验器     │
   │        │  ──────────────────────────────────     │

   │        │   │  工作流们（住在引擎里，复数）          │   │
   │        │   │  ＝ 定义数据（图谱/节点/规则/开工单表单）│   │
   │        │   │  ＋ App声明（探针/旗标/案台事实行）    │   │
   │        │   │  （需求分析 / 交付转报价 / 趋势…）     │   │
   │        │   └─────────────────────────────────┘   │
   │        └──────┬──────────────────────────┬───────┘
   │      I2 调工具 │                I1 声明注册 │
   │      I3 查探针 │                          │
   │               ▼                          ▼
   └──────────▶ ┌─────────────────────────────────┐
                │        业务系统（复数）             │
                │  CPQ：页面 · 服务函数 · 数据库       │
                │  人事培训系统：同结构（将来）          │
                └─────────────────────────────────┘
```

注意三条**画出来的线**怎么走的：

- **工作流 → 业务系统：没有直线。** 工作流要用业务的能力，只能调引擎的工具执行器（I2），由执行器去调业务的服务函数。
- **业务系统 → 工作流：没有线。** 业务系统根本不知道有哪些工作流存在。工作流增删，业务系统零改动。
- **人的甲路是特权，不是漏洞。** 人可以直接用业务页面（甲路）；AI 和工作流永远必须走引擎（乙路）。**这条不对称，就是"AI 可信"的架构来源**——AI 做的每一件事都过闸、留账，人做事不需要。

## 2. 一次开工单的数据怎么流（时序）

以"上传成本表 → 出报价单"的交付流为例，完整走一遍。每步标注**谁→谁、传什么数据**：

```
 人            引擎（AI办公室）                业务系统（CPQ）
 │ ①开工单        │                             │
 ├──────────────▶│                             │
 │ (一句话/开工单表单/上传成本表)                  │
 │               │ ②装填(fresh:解绑旧实体,清状态槽) │
 │               │        ┌──▶ 工作流(交付流)     │
 │               │ ③现算案台│     (提供flow_key)  │
 │               ├────────────────────────────▶│ 跑探针查真表
 │               │ ◀──案台视图(商机/成本表/缺价/待确认)─│
 │               │ ④大脑回合(本案台digest+左栏规则+本步工具白名单)
 │               │ ◀─ 大脑说: 调"提交转报价"(参数…)  │
 │               │ ⑤执行器: 权限检查 → 生成预览      │
 │ ◀⑥确认卡──────┤ (预览+参数,问答协议)            │
 ├─批准(query_id)▶│                             │
 │               │ ⑦执行服务函数(与页面同一个函数)    │
 │               ├────────────────────────────▶│ 改真表
 │               │ ◀──写入结果(单据号/主键)─────────│
 │               │ ⑧回读验证(再查一次库核对)        │
 │               ├────────────────────────────▶│ 查真表
 │               │ ⑨审计落账(谁/何时/工具/参数/改了哪行/谁批)│
 │               │ ⑩事实回填给大脑 + 步骤指针前移     │
 │ ◀⑪事件广播────┤ (node_trace: 节点亮灯+产物引用kind/refs)│
 │ ⑫点产物卡      │                              │
 ├──────────────▶│ 渲染分发(按kind找注册的页面组件)   │
 │ ◀─真页面真数据──┼─────────────────────────────▶│ 只读展示
 │               │ ⑬循环③~⑫直到案台交割完毕(complete)│
```

从这 13 步里提炼的**四句数据流口诀**（记住这个，全部数据流就记住了）：

| 口诀 | 含义 | 为什么 |
|---|---|---|
| **读＝拉** | 引擎每轮现算案台，从不缓存业务状态 | "真相"只在业务库里；缓存=制造第二个真相=事故源（案台原则） |
| **写＝过闸** | 一切写操作走 权限→确认→执行→回读→审计 | 绕过任何一环=暗道；回读保证"说干了"=真干了 |
| **展示＝引用** | 产物卡只带 (kind, refs) 引用，不拷贝数据 | 点开产物=打开业务真页面，看的永远是当下真值 |
| **通知＝推** | 引擎向前端广播事件（画布亮灯、聊天流） | 前端只渲染事件，不反查业务库 |

## 3. 彼此之间需要的接口（完整清单）

| # | 接口 | 方向 | 传什么数据 | 谁实现 | 现状 |
|---|---|---|---|---|---|
| I1 | **声明注册** | 业务系统 → 引擎 | 工具清单（名/参数schema/读写/确认档/权限键）、页面映射（产物kind→页面组件）、实体模型 | 引擎定格式（发布校验器把关），业务填表 | 工具散装在 agent_tools.py 手写规格，待收编成声明表（方案第1步） |
| I2 | **工具调用** | 引擎 → 业务系统 | 工具名+结构化入参 → 事实块+回读结果 | 业务写函数本体（与页面共用），引擎包执行器 | 已有（进程内直调 delivery_core）；外部系统时改走标准 API |
| I3 | **案台探针** | 引擎 → 业务系统 | flow_key → 案台视图（各步骤产物是否已落等现状事实） | 业务提供查询（将来降级为 DSL 填表） | 已有（delivery_app 手写探针，第二个应用出现时抽 DSL） |
| I4 | **事件广播** | 引擎 → 前端 | pipeline_start / node_trace(节点+状态+产物引用+耗时) / pipeline_waiting / pipeline_done / error | 引擎实现 | 已有（10-21 两台运行时对齐同一套词汇） |
| I5 | **问答协议** | 引擎 ↔ 人 | HumanQuery（consent/choice/form 三型）→ 人 Answer（按 query_id 结构化回） | 引擎实现 | 已有（10-23 建成，"一回合一问"是协议不变量） |
| I6 | **产物渲染** | 前端 → 业务页面组件 | artifact(kind, refs) → 打开对应真页面 | 业务注册组件，引擎分发 | 已有（NodeArtifactModal），kind 注册表待后端单源 |
| I7 | **审计** | 引擎 → 账本；人 → 查询 | 谁/何时/哪个回合/工具/参数摘要/前后引用/确认者/actor身份 | 引擎实现（字段命名对齐 gen_ai.*） | 待建（方案第 3 步"上安全带"） |
| I8 | **开工单/装填** | 人 → 引擎 | 意图文本 / launch 表单字段 / 附件 | 引擎实现 | launch 表单已有（通用底座） |

规律：**业务系统只需要实现 I1 的"填表"和 I2/I3 的"函数本体"**——其余全部是引擎的代码。这就是"业务系统不写 AI 代码"在接口层的落点。

## 4. 谁拥有什么数据（所有权是边界，边界就是安全）

| 数据 | 拥有者 | 别人怎么碰 |
|---|---|---|
| 业务数据（商机/成本表/报价单/配件价/规则表…） | 业务系统（唯一事实源） | 引擎经 I2/I3 现查现用，**绝不复制、绝不缓存** |
| 会话/线程、确认记录、审计账本 | 引擎 | 业务系统不读不写（它不需要） |
| 工作流定义（图谱/节点配置/左栏规则/开工单表单） | 工作流（存在 DB，引擎只读执行） | 人经画布改，改时过发布校验器 |
| 状态槽（探针查不到的旗标，如"加价已执行"） | 引擎（AI 侧临时便签） | 按页面代理总纲**最小化**——能从真表现算的绝不存便签 |
| 产物 | 不是数据，是**引用**（kind+refs） | 指向业务真页面，永远展示当下真值 |

一句话：**真相只有一份，在业务库里；引擎和工作流只存"指针、便签和账本"。**

## 5. 三条"没有的线"（没画出来的比画出来的更重要）

1. **工作流 ⇄ 业务系统：没有直线。** 所有读写必过引擎执行器——因为卡（拦截）、账（审计）、回读（核实）全在执行器里。谁绕过执行器直连业务库，谁就把确认卡和审计整个甩开了，这在本系统里被定性为**暗道=事故源**（护栏已写进内核："应用只能声明，不能带自己的编排逻辑"）。
2. **业务系统 → 工作流：没有感知线。** 业务系统不知道自己被哪些工作流使用。将来删一条工作流、加一条工作流，业务系统一行不改——这是"系统与 App"关系的检验标准。
3. **AI 的旁路：没有。** 人有甲路（直接用页面），AI 没有——AI 的一切动作必须留痕于引擎。将来任何时候有人提议"给工作流开个直连业务的快速通道"，拿这一条拒绝他。

## 6. 今天 vs 目标态（诚实标注图的哪些部分还没建成）

| 图上元素 | 今天 | 目标态（方案五步走完） |
|---|---|---|
| 引擎与业务系统的物理关系 | 同进程寄宿（引擎代码住在 CPQ 后端里） | 模块边界干净（依赖守卫把守）→ 换宿主可跑（stub 演练）→ 独立部署（等真有第二宿主） |
| I2/I3 的调用方式 | 进程内函数直调 | 本系统仍是直调；外部系统走标准 API + 接入薄壳 |
| I1 声明注册 | 散装（工具规格手写、kind 硬编码前端） | 一份声明表 + 发布校验器把关 |
| I7 审计 | 日志堆 | 结构化审计协议 + 账本视图 |
| 工作流的探针 | 手写代码（delivery_app） | DSL 填表（第二个事务应用落地时抽取） |

**图的逻辑关系不随部署形态变**——同进程也好、独立服务也好，"谁拥有什么、哪条线不存在"一个字不变。这正是现在就把边界画死的意义：物理上可以搬，逻辑上不返工。

## 7. 自查清单（判断任何新设计是否破坏这张图）

给将来的自己（和 AI）立三问，改任何机制前先过一遍：

1. 这条新连线绕过引擎了吗？（绕过 = 暗道，否决）
2. 这个新状态能从业务真表现算出来吗？（能 = 不许存便签，否决）
3. 业务系统因为这条改动需要"知道某条工作流"了吗？（需要 = 耦合，否决）

三问全过，才准动工。
